### Bug: obs normalization explodes off-policy replay

**Symptom:** Q-values diverged to -15,000, alpha to 19+, returns stuck at 32.

**Root cause:** Online obs normalization + off-policy replay buffer = catastrophic mismatch. At env reset, all 128 envs have near-identical observations → variance ≈ 0 for some dims → `normalize()` divides by `sqrt(0) + 1e-8` → stored `next_obs` values hit ±2 billion → TD targets at ±47 million on first gradient step.

**Why it only affects SAC, not PPO:** PPO is on-policy — obs are normalized and consumed in the same batch, so the normalization stats match the data. SAC's replay buffer stores normalized obs that become stale as norm_state evolves.

**Fix:** Removed obs normalization entirely for SAC. Matches Brax reference (which also doesn't normalize). The Q-network's LayerNorm provides implicit input normalization. Initialized norm_state as identity (mean=0, var=1) for checkpoint compatibility.

**Bugs found during TD3 bringup:**
1. **ActLoss always 0.000** — with `policy_delay=2` and `grad_updates_per_step=1`, every other gradient step skips the actor update and returns dummy metrics. Fixed by tracking last real actor loss separately.
2. **Replay ratio too low** — vanilla TD3 uses 1:1 (1 gradient step per env step) for single-env. With 128 parallel envs, we collect 128x more data per step. Bumped `grad_updates_per_step` to 4 in presets.

### Deterministic eval protocol
Added shared `jax_rl/utils/eval.py` — runs N deterministic episodes on a separate env instance (separate JIT, doesn't touch training pipeline). Triggered by episode count (`eval_every_n_episodes` in TrainConfig), plus a final eval after training completes. Integrated into all three train scripts (PPO, SAC, TD3).

Config additions to TrainConfig:
- `eval_every_n_episodes: int = 500`
- `num_eval_episodes: int = 10`

Bug found during integration: end-of-training eval didn't fire because `total_env_steps // num_envs` truncates — last iteration's step count is always slightly below `total_env_steps`. Fixed by moving final eval outside the training loop.

### FastTD3 implementation — C51 distributional critic
Built FastTD3: TD3 + C51 distributional critic + Q averaging + LR cosine decay.

**New files:**
- `jax_rl/algos/fast_td3.py` — distributional critic loss with C51 projection
- `jax_rl/networks/heads/q_distributional.py` — outputs (batch, 51) logits instead of scalar
- `jax_rl/utils/distributional.py` — C51 projection, cross-entropy loss, support utilities
- `jax_rl/configs/fast_td3_config.py` — FastTD3Config with C51 params
- `train_fast_td3.py` — training script with LR cosine decay

**Bugs and tuning issues:**
1. **V_min/V_max too narrow** — default [-10, 10] from paper capped Q at 10, but CheetahRun Q should be ~80. Widened to [-10, 150] per env.
2. **Batch size mismatch** — paper uses batch=32K with 1024+ envs. At 128 envs, batch=8K starves the model (too few fresh transitions per batch). Reduced to 512 for 128-env runs.
3. **Scale mismatch** — FastTD3 runs for ~750M steps at 1024 envs (3 hours on A100). Our 5M-step runs at 128 envs had 155K gradient steps vs paper's ~9M. The paper's advantage is wall-clock speed at massive scale, not sample efficiency at small scale.

**Results at 5M steps (not paper scale):**
- batch=8192, 128 envs: 171 avg (below vanilla TD3's 749)
- batch=512, 128 envs: 285 eval (still below vanilla TD3)
- 4096 envs, batch=8192: 21 eval (only 4856 gradient steps — broken replay ratio)

**Now running at paper scale:** 1024 envs, batch=8192, 12 grad updates/iter, 100M steps.

### JAX-native replay buffer
Built `jax_rl/buffers/jax_replay_buffer.py` — same interface as numpy version but data lives as `jax.Array` on GPU. Key design: JIT'd sample function cached per batch_size, giving constant ~0.15ms sample time regardless of batch size (vs numpy's 1.74ms at batch=32K).

Benchmark (sample only, post-JIT warmup):
| Batch size | Numpy | JAX JIT | Speedup |
|-----------|-------|---------|---------|
| 512 | 0.33ms | 0.12ms | 2.7x |
| 8,192 | 0.72ms | 0.15ms | 4.8x |
| 32,768 | 1.74ms | 0.13ms | 13.3x |

Integrated into all off-policy train scripts via `--jax-buffer` flag (SAC, TD3) or default (FastTD3, FastSAC).

End-to-end throughput improvement for FastTD3 was marginal (~1.5%) because gradient steps dominate. Real payoff requires `jax.lax.scan` over the inner gradient loop to eliminate Python dispatch.

### Scanned gradient loop — attempted and reverted
Tried `jax.lax.scan` over the inner gradient loop (sample + update × N) to eliminate Python dispatch overhead. Three iterations:

1. **Pre-sample approach:** sample N batches in Python, stack, scan updates. 30% slower (10 dispatches for sampling + stack overhead, was 16 for Python loop but lighter).
2. **Sample inside scan:** buffer arrays closed over in scan body. OOM — JAX embedded 4M-entry buffer as XLA constants.
3. **Buffer as explicit carry:** passed buffer arrays as scan carry arguments. No OOM but 30% slower — threading 6 × 4M arrays through carry every iteration dominates dispatch savings.

Microbenchmark with 100K buffer showed 1.17x faster. Full training with 4M buffer showed 0.70x (slower). The carry cost scales with buffer size.

**Reverted SAC to Python loop.** Removed `scanned_update.py` — the carry overhead made it slower in every real training scenario (4M buffer SAC, 1M buffer FastTD3). Not worth keeping dead code around for a hypothetical future where JAX improves carry handling.

## Lessons
- **Online obs normalization is incompatible with off-policy replay** — the near-zero variance at env reset produces enormous normalized values. Either normalize at sample time (complex) or skip normalization entirely (simpler, matches Brax SAC)
- **LayerNorm in Q-networks serves double duty** — stabilizes training AND implicitly handles input scaling, making explicit obs normalization unnecessary for off-policy methods
- **SAC's sample efficiency vs PPO is dramatic** — WalkerWalk: 975 at 5M vs 833 at 60M. HumanoidRun: 23+ at 1M vs ~10 at 60M. Off-policy + 8 gradient updates per step = serious leverage
- **Replay ratio must scale with num_envs** — vanilla TD3's 1:1 ratio assumes single-env. With 128 envs, grad_updates_per_step must increase proportionally or the model can't keep up with data collection
- **Policy delay + low grad_updates_per_step = invisible actor** — with delay=2 and updates=1, half the logged steps show dummy actor_loss=0. Track last real actor loss separately for accurate logging
