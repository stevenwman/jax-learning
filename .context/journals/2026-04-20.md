## The `reset_mode` footgun (fix #5)

Pilot v1 (5M steps, no `--reset-mode per_step` flag) ran for 3h and produced `mean_level=0` everywhere. Type distribution was `rough=4, pyramid_up=11, pyramid_down=7, tilted=10` (totaling 32 but not 8 each). Indicates terrain_type was being randomized per-episode by the **inner** env's reset, with no wrapper overriding it back.

Root cause: `TerrainCurriculumDRWrapper` is only applied in `env_setup.make_envs` when `cfg.reset_mode == "per_step"`. `TrainConfig.reset_mode` defaults to `"legacy"`. My launch command didn't pass `--reset-mode per_step`, and the curriculum preset didn't set it. Training ran with plain AutoResetWrapper, no curriculum logic.

Surprising that the training didn't crash — the env functions fine, reward/obs still valid, episodes still complete. It just has no curriculum. Added `reset_mode="per_step"` to all curriculum presets (PRESETS, FAST_SAC, FLASH_SAC) so future launches can't forget.

Symptom to watch: if distribution deviates from `num_envs / num_cols` per type, wrapper isn't running.

## Throughput + comparison to published pipelines

v5: 341 sps total across 32 envs = ~10.6 sps/env. 

Bottleneck is **VRAM**, not FLOPs: 16GB RTX 5080 caps us at 32 envs (curriculum env has ~1500 geoms vs ~100 on flat). 32 envs poorly amortize Warp kernel dispatch overhead.

- MJLab (same MuJoCo Warp backend), Go2 flat PPO, 1024 envs → ~15 sps/env total ~15k sps
- RSL-RL (Isaac Gym), anymal_c, 4096 envs, PPO → ~20-50 sps/env
- MuJoCo Playground (Brax), Go2 flat PPO, 4096 envs → ~15-25 sps/env

Per-env throughput is on par. Total wall-clock is 30-50× slower because we're memory-limited to 1% of their parallelism. SAC (UTD=8) also halves throughput vs PPO. Not a GPU speed problem, a GPU memory problem.

## Termination debugging (fix #4)

Original `_get_termination` inherited from parent: `flipped | base_z < 0.18` (world frame).

- **pyramid_down L5:** robot standing at pit bottom has `base_z ≈ -0.7m`. Auto-terminates on every episode regardless of policy → `mean_level` clamped at 0 for pyramid_down.
- **elevated terrain (pyramid_up ring_height > 0.2m):** robot standing on ring has `base_z > 0.5`, doesn't fire even when torso actually collapses but stays in absolute frame.

Fix: `flipped | base_contact > 0` using `<contact body1="base_link" reduce="mindist" num="1" data="found"/>` sensor added to scene template. Probe script confirmed sensor fires on both CPU MuJoCo and Warp backends: 0 when upright, 4 (num contact points) when torso flat on floor.

Deliberate exclusion: robot lying on side with legs propped has `base_contact=0, upvector_z~0.8`. Not terminated — leg contact is fine, policy may still recover. Flipped check catches full inversions.

Added two regression tests (`test_flipped_robot_triggers_termination`, `test_standing_in_bowl_does_not_terminate`).

## The unified redesign (fix #7)

Dual-class had practical issues:
- Class A random Bernoulli cmd sends robot out of tile in ~10s. Robot spends half the episode on neighbor's physics.
- Class A promote criterion went through two rewrites (max_dist → tracking-error), both ad-hoc thresholds.

User's insight: **if all types use goal-directed holonomic cmd + random yaw, the rotating body frame naturally produces omnidirectional linvel DR**. As yaw spins, the fixed world-frame goal direction sweeps through every body-frame angle. Richer than discrete Bernoulli step-jumps.

Unification:
- All 4 types: spawn rim, goal at tile center, holonomic body-frame cmd
- Single promote rule
- Single demote rule
- Drop Class-A-specific state fields (`episode_max_dist_from_spawn`, `episode_tracking_error_sum`, `episode_step_count`)
- Drop `_IS_GOAL_DIRECTED` gating everywhere

v5 confirms this works: 4× faster advancement than v3 at same step count.

## Zero linvel after reach (fix #8)

Once robot enters 0.5m goal zone, `episode_reached_goal` latches True. Flip cmd_vx/cmd_vy to zero. Robot stands and tracks random yaw (from parent's sampler) for the rest of the episode.

Benefits:
1. Full 20s episode used for data
2. Explicit "stop at target" behavior
3. Yaw controller exercised at zero linvel (common deployment requirement)
4. Eliminates dist≈0 numerical degeneracy in goal-direction normalization

Implementation: read `episode_reached_goal` **inside** the `_override` closure. When called post-super().step(), the closure sees the freshly-flipped value.

## Eval OOM investigation — non-issue

Killed v5 at 3.06M to investigate. Ran `/tmp/eval_oom_probe.py` which instantiates both train+eval envs via `make_envs`, runs one train step, then eval reset + step, measuring GPU memory between each phase. Curriculum env at num_envs=32:

```
baseline → make_envs (train+eval):    +504 MiB
make_envs → train first step:         +28 MiB
train → eval_env.reset:               +0 MiB  ← cache shared
eval reset → eval_env.step:           +0 MiB  ← cache shared
total curriculum footprint:           ~500 MiB
```

**Warp compiles kernels per-env-class, not per-instance.** Both `WarpJoystickCurriculum` instances share the kernel cache. The hypothesis that eval_env doubles VRAM was wrong.

Historic eval OOMs that prompted the workarounds were from: (a) `num_envs=64+` at the time, (b) training replay buffer + grad activations filling VRAM, eval just the straw that broke the camel, (c) GPU contention with other processes.

Lesson: before piling workarounds on top of a historical warning, verify the failure mode still applies under current config. My `--eval-every 9999999` on v2-v5 pilots threw away all intermediate checkpoints based on a fiction. Future runs should use `eval_every_n_episodes=5000` as configured.

## Log-barrier: match reward curvature to metric curvature

Linear `r_coverage = cov` gives flat marginal (1pp of cov = 0.01 reward regardless of level). But coverage is geometrically nonlinear — 2px displacement drops 5% coverage near the goal. Linear underpays precision, policy plateaus at 85%.

Log-barrier: `r = -log(1 - clip(cov/thresh, 0, 1) + ε)`, ε=0.01. Ceiling 4.6 at cov≥threshold.

```
cov    linear    log_bar
0.5    0.53      0.73
0.7    0.74      1.30
0.9    0.95      2.77
0.95+  1.00      4.60
```

Marginal reward ∝ `1/(1-cov+ε)`. At cov=0.9, gradient is 9× steeper than at cov=0.5. Policy actually chases the last few percent.

**Cost:** Q magnitudes grow ~3-5× (Q1 goes from +30 → +90 stable). No instability at `reward_scale=0.1, grad_clip_norm=1.0`. First-ever success event observed on minimal_logbar (cov=0.9511, terminated step 27 of 150) — previous runs never crossed 0.95.

## Action repeat is the dominant knob

Stripping AR=2→1 collapsed from 0.933 → 0.522 sto. Largest effect of any single ablation. Reason: push-T needs sustained directional force on the block. At AR=1 (10 Hz policy), small policy oscillations reverse pusher direction mid-push; block barely moves. AR=2 (5 Hz policy) commits each action for 2 env steps → block accumulates velocity.

Also halves decision count → fewer noisy Q targets → more stable learning. Q1 range: AR=2 stable ~+90, AR=1 oscillates into negative. Alpha (entropy coef) also bounces 0.04 with AR=1 vs stable 0.02 with AR=2.

Generalization: action chunking (Q-chunking NeurIPS 2025, Q-LAC ICML 2025) extends this to K-step committed action sequences. Needs flow-matching or diffusion actor for inter-action correlation. Deferred in TODO.md — plan to revisit with upcoming flow-matching off-policy work.

## Minimal shape-agnostic config wins

Cross-shape transfer needs shape-agnostic obs (keypoints have shape-specific vert count — 8 for T, 60 for S ribbon). Tested `state(5d) + FS=1 + AR=2 + log_bar`:

- Det: 0.906 (vs full-stack baseline_logbar 0.867) — +4pp
- Sto: 0.939 (vs 0.933) — +1pp, plus first success event

Surprise: minimal *beats* full stack. Under strong log_bar reward, richer obs (FS=3 on 5d state = 15d time-shifted duplicates) adds input noise without useful velocity signal. Critic fits simpler distribution → lower-variance Q.

Single-seed runs so some noise possible, but direction clear. **Cross-shape baseline locked:** `state + FS=1 + AR=2 + log_bar + contact_gated`.

## Bigger success bonus doesn't raise ceiling

bigbonus_logbar (success_bonus 50→200): det tightened +5pp (std 151→27), sto unchanged. Reason: policy never crosses 0.95 threshold during training → never samples the terminal. Making an unobserved bonus larger doesn't change learning — only tightens trajectory distribution near-but-below threshold.

Lesson: verify terminals actually fire during training before tuning bonus magnitude.

# Push-T Cross-Shape Geometry + Zero-Shot Transfer (2026-04-20, evening)

Third session. Designed 4 new block shapes (ellipse, iso-triangle, letter S, letter U) for the cross-shape benchmark and ran a zero-shot transfer test using the `minimal_logbar` policy to verify the plumbing end-to-end. Recording infrastructure validated — all 5 shapes render and simulate cleanly in pymunk, policy can act, videos save. Transfer results confirm zero-shot is a **floor**, not a working baseline; shape-aware training is the next milestone.

## Shape design — annular-sector decomposition

Letters S and U are concave; pymunk requires convex `Poly` geoms. Iteration history (worth noting but not worth saving as lessons):

1. **Sinusoidal-ribbon S** — centerline sampled from `x = A·sin(2π·y/H)`, thickened perpendicular. Good body curve but visible "fins" where bezier curvature tight (hook tips).
2. **3-bezier centerline** — upper dome + middle diagonal + lower dome, C¹-continuous. Better topology but still fin artifacts.
3. **Two overlapping annular sectors** (winner). Each "lobe" is a 270° fat ring (inner_r=22s, outer_r=38s). Uniform curvature because every wedge quad is tangent to a circle — no tangent-mismatch artifacts by construction.

Final S geometry (in `tools/record_pusht_shapes.py`):
- Scale: s=1.367 (30% smaller than initial 1.95 pick)
- Ring thickness: `outer_r - inner_r = 16s ≈ 22 px`
- Hook interior: `inner_r = 22s ≈ 30 px` (pusher radius 15 → 15 px margin)
- Upper lobe center: `(0, 27s + block_height·3/14)` — shifted up by ~6.7 px (1/7 of quad radial thickness + half that) for better optical alignment
- Arc span: 270° per lobe (end wedge trimmed for tapered tip, outer hook preserved)
- 9 wedges/lobe × 2 lobes = **18 convex quads**

U is similar: 180° half-ring (10 wedges) + 2 rectangular arms = **12 convex polys**. Ellipse = single 32-vert convex poly. Triangle = single 3-vert poly.

## Shapely topology issue

`_get_coverage` crashed on shapes with overlapping convex pieces (S, U):

```
GEOSException: TopologyException: side location conflict at ...
```

Root cause: `pymunk_to_shapely` builds `sg.MultiPolygon` from pymunk's per-shape vertex lists. When pieces overlap (by design for S's two-ring construction), the MultiPolygon is self-intersecting — GEOS rejects it. `MultiPolygon ≠ polygon with holes` in shapely.

Fix for vibes-only recorder: try/except → return 0. Proper fix for training: `unary_union(pieces).buffer(0)` — the `buffer(0)` idiom heals self-intersections into a valid polygon. Deferred until cross-shape training actually runs.
