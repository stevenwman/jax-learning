## Lessons

- **Q bias is the cleanest diagnostic for truncation handling.** On long-horizon tasks, post-fix Q bias should be near zero. If it's negative-biased, the fix isn't applied or the wrapper isn't populating `info["truncation"]`. Add to the smoke-test checklist.
- **CheckpointManager "best" excludes final eval.** Either fix the manager to also check the final eval against `best_eval`, or just always take `max(best_in_loop, final_eval)` when reading benchmarks. Lower-priority code cleanup.
- **FlashSAC needs more Warp memory headroom.** Larger networks → JAX heap eats more of the 0.7 fraction → less left for Warp graph capture. `XLA_CLIENT_MEM_FRACTION=0.55` is the FlashSAC-specific default. Worth bumping in `train_flashsac.py`'s `os.environ.setdefault` so users don't hit the OOM.
- **TODO line items can lie about preset values.** `# uses preset 10M` was wrong (preset is 100M). When writing TODO commands, paste the explicit `--total-timesteps` rather than relying on memorized preset values.
- **Velocity "kick" vs force "push" is universal terminology drift.** Across legged_gym/Isaac Lab/RSL-RL/Playground, everyone calls it a "kick" but implements it as direct `qvel` injection (mass-invariant, deterministic). Calling it a "force" would be wrong; calling it a "velocity perturbation" would be pedantically correct; calling it a "kick" is field convention. Code comment/var name in `go2_warp_joystick.py:304-313` uses "kick" + "push_vel" interchangeably — slight inconsistency, low priority.

## Follow-up: `record_video.py` memory investigation + refactor

User came back asking why Warp graph capture would be so big for "just 1 env 1 traj". Dug deeper and the original `lessons/infrastructure.md` entry was partly wrong — it blamed graph capture for the whole 1.5 GiB while dismissing the trajectory buffer as ~1 MB. Actual breakdown:

1. **`lax.scan` output preallocation: 500 MB–1 GB.** The scan allocates buffers for the *full mjx State × 1000 steps* upfront. State isn't qpos/qvel — it's the full MJX Data struct with ~50 fields (`qM` nv×nv, `cinert`/`crb` nbody-shaped, padded `efc_*`/`contact.*` arrays, info dict with reward_components). For Go2 that's ~0.5–1 MB/step × 1000.
2. **Warp graph scratch: 100–500 MB.** `_default_nconmax=48, _default_njmax=64` for Go2, padded further for JtDAJ tiling. Per-step tiny, but Newton solver (`iterations=100, ls_iterations=50`) + elliptic cone + hundreds of kernels (collision_*, constraint, solver, smooth, sensor, passive, forward, derivative) accumulates captured-graph workspace.
3. **XLA compile working buffers: tens-hundreds of MB.**

Sum ≈ 1–2 GB, matching the observed 1.49 GiB failure.

**Refactor decision:** `lax.scan` is a *training* pattern — amortize compile over many rollouts, full traj is your data. For *one-shot inference* it's the wrong default. Replaced with a Python loop over `jax.jit(rollout_step)`: one State buffer reused each iter, host-side lists accumulate only the fields we need (qpos, qvel, action, reward, commands, reward_components). Bonus: natural `break` on `done` instead of post-hoc slicing.

**Landed:**
- `os.environ.setdefault("XLA_PYTHON_CLIENT_PREALLOCATE", "false")` baked into `record_video.py` — handles the preallocator-vs-Warp contention that happens inside `env.reset` (before the scan/loop even starts).
- `lax.scan` → Python loop — drops steady-state peak ~500 MB–1 GB. NPZ output schema preserved (22 keys, identical within float32 noise: 1e-7 at step 0, drifts to 1e-4 by step 199 — chaotic divergence, not a bug).
- Removed dead `jnp` import.

**Why both fixes, not just one:** the env var alone fixes the *contested-GPU* case. The Python loop additionally fixes the *concurrent-training* case — running a render while training on the same GPU would still OOM with the scan pattern because training's preallocator + render's 1 GB scan peak exceeds available.

**Things I initially got wrong mid-investigation:**
- Reflexively listed "dispatch overhead" as a con of the Python loop. 50–200 ms over 1000 steps is nothing vs the ~30s CPU render phase. User correctly pushed back on this.
- Proposed JAX compilation cache (`jax_compilation_cache_dir`) as a time-saver. User correctly noted they don't invoke record_video multiple times in a normal session — caching solves a problem that doesn't exist in this workflow. Dropped it.
- Underweighted the "Python loop is the right architectural fix" angle because the env var workaround was already solving the proximate bug. User pushed on "idk why you're so against the python loop" and they were right.

## Lessons (additional, from the follow-up)

- **`lax.scan` is wrong for one-shot inference scripts.** It's a training pattern — justified when you amortize compile cost over many rollouts and actually need the full trajectory. For single-rollout tools like `record_video.py`, the scan preallocates a full-State × N buffer for nothing. Python loop over jitted step is simpler, uses less memory, compiles faster, and supports early-stop naturally.
- **"1 env, 1 traj" is misleading framing for memory.** Warp pads `nconmax`/`njmax` to worst-case tile sizes regardless of actual contact count. The full mjx State is ~50 fields with nbody/nv/nefc shapes, not just qpos/qvel. Any trajectory-scan memory analysis has to account for the full struct, not the "interesting" fields.
- **When proximate bug is fixed, reassess the architectural fix on its own merits.** The `PREALLOCATE=false` workaround solved the immediate OOM, which made me underweight the scan→loop refactor. That was a mistake — the loop has independent benefits (memory coexistence, cleaner control flow, faster first-run compile). "The symptom is gone" ≠ "the right code is in place".
