# 2026-04-08 — DRv2 Training Comparison & Syncd Rabbit Hole

## Summary

Continued DRv2 work from yesterday. Spent most of the day debugging syncd mode integration issues before pivoting to per_step mode, which turned out to be the right answer all along.

## The Syncd Saga

### The appealing idea
Syncd mode: all envs step together, batch reset when done. No per-step reset overhead. Benchmarks showed 2x raw throughput vs legacy.

### What went wrong
1. **"4x slowdown" was a ghost.** Compared cumulative SPS (includes JIT warmup) vs converged SPS. Wasted 2+ hours. Legacy also starts at ~368 sps. Both converge to ~3,400.
2. **GPU sync bug.** Per-step `np.asarray()` for waste tracking killed async GPU execution. Real ~8x slowdown from one line.
3. **EpisodeTracker broken.** Syncd `done` is sticky (stays 1.0 for dead envs). Tracker counted every step as a new episode → 51k "episodes" in 60k steps. Fixed with `_newly_done` masking.
4. **Reward accumulation leak.** Tracker's `episode_rewards` didn't reset on batch reset → stale rewards carried across rollouts.
5. **Buffer pollution.** Post-done transitions (reward=0, garbage obs/actions from tumbling dead robots) fill the replay buffer.
6. **Waste fraction logging.** `instant_waste` (point-in-time snapshot) was useless. Needed cumulative tracking without GPU sync. Multiple iterations to get right.
7. **Episode count still wrong** after the tracker fix turned out correct — was reading stale log from a previous run.

Each fix revealed the next bug. 6+ relaunches to get a clean run.

### The waste problem
Even with "reset when all done" optimization, waste was 60-95% in early training. Envs die at step ~50, wait until step 1000 (or until all 256 die). The 2x raw throughput gets eaten by waste → worse effective sample efficiency than legacy.

At 1.9M raw steps: syncd avg_return 15.7 vs legacy 250.3. Not even close.

## The Pivot to Per_step

Per_step DRv2 = compute reset for all envs every step, select via where_done. Functionally equivalent to AutoResetWrapper(full_reset=True) but in one wrapper.

### Results (5M step comparison on wandb, seed 0, 256 envs)

**Throughput (converged):**
- Legacy: 3,400 sps
- Per_step: 3,200 sps (6% slower)

**Sample efficiency (at ~236s wall clock):**
- Legacy: 850k steps, avg_return 167
- Per_step: 800k steps, avg_return 199

Per_step learns faster despite being slightly slower. Fresh ICs help.

**5M run completed.** Per_step: eval 280.1, avg_return 265.9, 3,791 sps, 22 min. Legacy: eval 270.3, avg_return 248.8, 3,950 sps, 21 min. Per_step is slightly better final performance, 4% slower. Fresh ICs help.

## Key Technical Lessons

1. **Never compare cumulative SPS across runs.** JIT warmup dominates early numbers. Compare at same wall clock time after warmup.
2. **One `np.asarray()` per step = death.** GPU→CPU sync every step breaks async execution. Only sync at log time.
3. **Sticky done breaks everything.** EpisodeTracker, buffer, logging all assume done pulses once. Syncd's sticky done requires special handling everywhere — not worth the complexity.
4. **Dead envs don't slow physics** but they waste effective steps. The throughput gain from skipping reset is negated by stepping dead envs.
5. **Integration > algorithm.** DRv2 env stepping works perfectly in isolation. 80% of effort was tracker/buffer/logging integration bugs.

## Decision

**Per_step mode for Go2, legacy for everything else.** 6% throughput cost, better sample efficiency, enables per-episode DR. CheetahRun can't use per_step (catastrophic slowdown from full_reset), stays on legacy.

## Late Night: CheetahRun Per_step Test

**Result:** 6,309 sps (fast!), but `Eps 0, Return NaN`. No episodes completing.

This disproves our assumption that per_step/full_reset=True is catastrophically slow for CheetahRun. The isolated benchmark's 99% slowdown was likely a different bug (possibly the same NaN/episode issue causing the solver to iterate on bad state).

**Root cause of NaN/0 episodes: NOT A BUG.** CheetahRun never triggers done (running task). First truncation at step 1000. With 1024 envs, that's `1024 * 1000 = 1,024,000` raw steps before the first episode completes. We killed the run at 729k — 712 outer steps, hadn't reached 1000 yet. `Return NaN` is just the tracker having an empty completed_returns list.

**Implication: the 99% AutoResetWrapper slowdown on CheetahRun is likely also not real.** That benchmark only ran 500 steps — same situation, never hitting truncation. Something about the full_reset=True JIT graph on CheetahRun may have been compiling differently. DRv2 per_step compiled fine and ran at 6,309 sps.

**DRv2 per_step may work for ALL envs, not just Go2.** Need to run CheetahRun past 1000 steps to confirm episodes complete correctly.

## FlashSAC record_video Fix — Missing BatchNorm Stats in Inference Artifact

### The Bug

FlashSAC's `record_video.py` rollout showed instant falls (26-45 steps, reward ~10) on all seeds. FastSAC rollouts from same script ran full 500 steps with reward 135-142. Training eval reported 282.4.

### Root Cause

`actor_params.npy` (lightweight inference artifact) was missing `actor_batch_stats`. The code to save batch_stats was added in commit `f2e9e6f` (10:36 AM) — AFTER the training checkpoint was written (10:25 AM). Without trained BN running stats, the actor used init-time zeros/ones → garbage activations → instant falls.

The full orbax checkpoint (saved for training resume) DID contain batch_stats. The inference artifact was simply incomplete.

### Fix

1. Extracted `actor_batch_stats` from orbax checkpoint, patched both `best/` and parent `actor_params.npy`
2. Added `os.environ.setdefault("MUJOCO_GL", "egl")` to `record_video.py` — fixes headless rendering without requiring `MUJOCO_GL=egl` prefix

### Validation

After patching:
- Seed 0: 137.9, full 500 steps
- Seed 1: 134.0, full 500 steps
- Seed 2: 142.4, full 500 steps
- Seed 3: 136.8, full 500 steps

Matches FastSAC single-env rollout quality (135-142).
