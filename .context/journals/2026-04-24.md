# 2026-04-24 — Critic-norm + reward-norm persistence + schema-from-ckpt

Three correctness fixes shipped today, all in the same theme: state that needs to persist across train→deploy or train→resume boundaries was getting silently dropped.

## Privileged-obs normalization (commit 4562307, 1c6ed7d)

**Was:** off-policy with `has_privileged=True` passed raw critic_obs to algos and `q_fn` eval. On-policy maintained `critic_norm_state` in-process but never persisted to checkpoint — resume reset stats. Net: silent divergence between on/off-policy paths and across resume.

**Fix:** unified critic-norm primitives in `obs_pipeline.py` (`init_critic_norm_state`, `update_critic_stats`, `normalize_critic`, `make_critic_norm_fn`). Off-policy threads `critic_norm_state` through update + save/load + q_fn lambdas. On-policy persists via ckpt. `checkpointing.py` adds backwards-compat fallback for pre-fix ckpts (orbax try/retry on schema mismatch).

**Verified:** 13 new tests (11 obs_pipeline + 2 checkpoint), 80 tests pass total. Smoke runs Go2WarpJoystickFlat 2M @ 256 envs:
- FastSAC: eval **273.2 ± 3.7**, Q stable ~8.8.
- PPO: return 1.4→165, VLoss stable.

**Independently reviewed.** Reviewer found 2 blockers I'd missed: orbax strict-schema fails on missing key (need try/retry), and resumed on-policy semantics with bandaid-trained ckpts. Both fixed before merge. Reviewer also caught my missed callsite — `q_fn` eval lambda was passing raw privileged_state to `get_q_value`. Fixed.

**Follow-up filed:** re-run PPO4 bongo baseline (eval 46.9, pre-fix) with corrected critic-norm to validate ContractionPPO comparisons.

## FlashSAC reward_norm_state persistence (commit 6a17f9b, 3fe429b)

**Was:** `reward_norm_state` (G_r, G_r_max, G_var, G_count) lived as a module-local variable in `train_flashsac.py:158`. Not in `TrainingState`. Not in ckpt. Resume reset stats — `G_r_max` is monotonic running max, may never recover for near-optimal policies; denominator drops; rewards briefly scaled UP by up to G_max×; can push Q-targets outside C51 support.

**Fix:** fold `RewardNormState` into `TrainingState` (parallels `noise_state` field). Orbax serializes via existing `training_state` entry — zero changes to checkpointing/eval_runner. Pattern matches reference Holiday-Robot/FlashSAC (`reward_normalizer.pt` is a first-class artifact there).

**Verified — but my first verification was sloppy.** I ran a CartpoleBalance smoke that showed RewScale ~8.6 post-resume (matching pre-resume ~8.4) and called the fix verified. User pushed back ("smell sus"), independent reviewer confirmed: 20k steps of re-accumulation post-resume could land on a similar denominator regardless of persistence. Test was confounded.

**Real verification:** loaded the checkpoint and inspected `reward_norm_state.G_count` directly:
- `G_count = 499,968` ≈ 7,812 outer_steps × 64 envs (matches 500k env steps exactly; fresh init = 0).
- `G_r_max = 33.28` (fresh = 0).
- Computed RewScale from ckpt = 8.4318, matches pre-resume log line 8.435 to 3 decimals.

Lesson learned: signal-based verification of state persistence is fragile when the signal is subject to fast re-accumulation. Inspect the state directly.

**Follow-up filed (🔥 high priority):** post-resume eval drop 996→747 on CartpoleBalance is NOT from reward_norm_state (now verified persisted). Audit identified: `JaxReplayBuffer` has zero save/load methods. Empty buffer on resume → 10k steps of random-uniform actions → policy degrades during initial gradient updates on OOD batch. Reference repo persists buffer. Three fixes ranked in TODO; cheapest is "skip random warmup on resume" (use restored policy to collect data instead).

## Deploy schema-from-checkpoint (commit 437f530)

**Was:** `deploy/obs_builder.py` hardcoded the actor obs layout. Only contract sim↔deploy was `obs_dim` (an int). Drift history:
- 2026-03-26: deploy written with `[linvel(zeroed), gyro, gravity, ...]` = 48d.
- 2026-04-10: sim removed `linvel` from actor (45d). Deploy not touched.
- (Later, commit 62ec4ae mislabeled "docs:"): sim added `accelerometer` to actor (back to 48d, different content). Deploy not touched.

For ~14 days, every Go2 ckpt would have failed sim2real silently — deploy fed real `gyro` data into the slot the policy interpreted as `accelerometer`. Total dim 48 == 48 → no warning.

**Fix:** treat the obs schema as part of the checkpoint. `save_checkpoint` writes `meta.json["obs_schema"]["state"]` = ordered term-name list (extracted via new `schema_from_obs_groups` helper, resolving `IncludeGroup` recursively). Deploy `ObsBuilder.from_checkpoint(ckpt_dir)` factory reads it and composes obs in saved order via a sensor-fetcher registry keyed by term name. Unknown term → clear ValueError pointing at the file to edit. Backward-compat: ckpts without `obs_schema` fall back to a printed default schema.

**Verified end-to-end on CPU:** fake `_obs_groups` → schema → meta.json → `ObsBuilder.from_checkpoint` → 48d obs with gyro at [0:3], accel at [3:6]. 9 deploy tests green covering default, drop_accel, reorder, unknown-term, with/without schema, schema extractor IncludeGroup recursion.

**Bonus cleanup:** dropped dead `VelocityEstimator` from `deploy/deploy_go2.py` (linvel hasn't been in actor obs for years). Added `WarpJoystickNoAccel` ablation env on the sim side (registered as `Go2WarpJoystickFlatNoAccel`); deploy auto-syncs via schema, no special case needed.

**Origin question driven by user.** I'd initially proposed a hardcoded patch (just sync deploy to current sim layout). User pushed: "shouldn't deploy infer from ckpt config?" That's the real fix. The patch I almost shipped would have prevented today's failure but not the next one. Schema-from-ckpt makes the failure mode structurally impossible.

## Theme

All three fixes share a shape: **state that lives across some boundary needs to be serialized at the boundary, not reconstructed by convention on the other side.**

- Critic-norm: saved with the ckpt, read on resume.
- Reward-norm: saved with the ckpt, read on resume.
- Obs schema: saved with the ckpt, read by deploy.

When the producer and consumer of a piece of state are decoupled in time or in code, "we'll just remember to update both" is not a strategy. It's not even a hope. We had three independent silent-divergence bugs from this anti-pattern, all caught in one day after one was tugged on.
