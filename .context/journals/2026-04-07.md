# 2026-04-07 — FlashSAC JAX Port

## Paper Review

Read Kim et al. "FlashSAC: Fast and Stable Off-Policy RL for High-Dimensional Robot Control" (arXiv:2604.04539, April 2026). Key innovations over our FastSAC:

- **Inverted residual blocks** with pre-activation BatchNorm — enables 6-layer networks without instability (condition number drops 5-10x)
- **Explicit weight normalization** — project Dense kernels to unit norm, BN scale+bias to √D norm after every optimizer step
- **Adaptive reward scaling** — normalize rewards by running return variance, bounds distributional critic support to [-5, 5]
- **Unified entropy target** — σ=0.15 for all tasks (no per-task tuning)
- **Zeta noise repetition** — temporally correlated exploration via power-law repeat lengths
- **Cross-batch (2B) forward** — concat obs+next_obs for shared BN statistics

Paper claims: 20 min sim training → real locomotion (vs PPO 3 hrs). Order-of-magnitude speedup on sim-to-real.

Comparison doc: `.superpowers/specs/flashsac_vs_fastsac_analysis.md`

## Design & Review

5 spec review passes caught 22 issues total. Most impactful catches:
- **Weight norm axis:** Flax kernel is `(in, out)` vs PyTorch `(out, in)` — normalizing `axis=-1` would have silently broken training (need `axis=0`)
- **Target BN stats not copied:** Target critics maintain own running stats via `train=True` forwards. EMA only updates learned params, not buffers.
- **C51 done signal:** FlashSAC uses `terminated` only (not `terminated|truncated`) for bootstrap, while reward normalizer resets on both
- **Update order:** Actor → temp → critic (opposite from FastSAC's critic-first)

Design spec: `.superpowers/specs/2026-04-07-flashsac-port-design.md`

## Key Design Decisions

1. **Standalone `train_flashsac.py`** — not integrated into `train_offpolicy.py`. FlashSAC has too many collection-time differences (noise repetition, reward stat tracking). Integrate later if results are good.
2. **Two separate critics** (not ensembled) — JAX's functional style makes separate `apply()` calls cleaner than fused ensemble ops. Can add `nn.vmap` later if profiling shows it matters.
3. **Reward norm state outside TrainingState** — simpler flow, no JIT boundary issues. Matches how `obs_norm_state` is handled in existing code.
4. **Vectorized noise** (deviation from reference) — per-env independent repeat cycles vs reference's scalar noise. Behavioral change that needs validation.

## DRv2 Wrapper Investigation (PM session)

### Summary
Deep dive into domain randomization architecture. Started with DR spec design, ended up discovering fundamental limitations in the reset/episode boundary infrastructure.

### Key discoveries
1. **Current DR is weak** — 256 fixed physics configs, never re-randomized per episode. Same as Brax.
2. **AutoResetWrapper(full_reset=True) is unreliable** — ranges from +24% (Go2) to -99% (CheetahRun) across envs.
3. **JAX can't do selective reset** — vmap lowers cond→select, both paths always execute. Isaac Lab avoids this via PyTorch tensor indexing.
4. **Zeroed qpos → 10-19x solver blowup** on Go2 (physically impossible state). Always use keyframe.
5. **Dead envs don't slow physics** — constant throughput regardless of waste fraction.

### Built DRv2Wrapper
- Two modes: per_step (where_done) and syncd (batch reset)
- Syncd: 2x raw env throughput in isolated benchmarks
- Training integration: unexplained 4x slowdown (470 sps vs legacy 3950). NOT caused by state.info size, nan_safe, buffer, tracker, or dead env physics. Root cause unknown — needs JAX profiling.

## Debugging Session (late PM)

### Bugs found and fixed

1. **Target EMA gated by policy_delay** — target networks only updated every 2 steps instead of every step. Reference calls `update_target_network` unconditionally. Fixed.

2. **Metrics display zeros** — actor_loss/entropy showed 0.0 on policy_delay skip steps. Added carry-forward logic (same pattern as train_offpolicy.py's TD3 handling). Fixed.

3. **Eval using stale BatchNorm stats** — `select_action` fell back to `_default_actor_bs` (set once at init, never updated). Eval used all-zeros running mean/var → garbage actions. Online return 686 but eval return 26. Fixed by updating `_default_actor_bs` from `training_state.actor_batch_stats` before every eval call.

4. **`tail -N` in background commands** — buffered ALL output until process exit, making it look like the process produced nothing. Not a code bug, but an operational gotcha with Claude Code background tasks.

### First benchmark: CheetahRun 5M steps

Config: `--num-envs 128 --grad-updates-per-step 4 --seed 100`

| Metric | FlashSAC | FastSAC (reference) |
|--------|----------|-------------------|
| **Eval return** | **619.6 ± 1.5** | ~800+ |
| Gradient steps | 155K | ~39K |
| Wall-clock | ~22 min | ~8 min |
| SPS | 3,700 | ~55K (1024 envs) |
| Q bias | -54.46 | — |

**Analysis:** Eval 619 is a solid first result but below FastSAC. The massive Q bias (-54.46, critic Q=3.35 vs MC=57.81) suggests the C51 support [-5, 5] is too narrow after reward scaling, or the adaptive scaling is too aggressive. The reference uses `normalized_G_max=5.0` but with `gamma=0.99` and CheetahRun rewards ~10/step, actual returns are ~1000 — even after scaling, the support may clip.

### Remaining issues
- Q underestimation: investigate C51 support bounds vs actual scaled returns
- num_envs default (64) too low for parallel training — should match FastSAC (1024) or use higher UTD
- Need proper A/B with matched wall-clock budget
