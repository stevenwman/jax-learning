# 2026-03-12 — First Training Curve + JIT Deep Dive

## What we did

### PPO Training on CartpoleBalance
- Wired up the full training loop: env, collect loop, GAE with truncation handling, PPO update, obs normalization
- **Result:** 995.4 avg return in ~85s (1M steps, 244 iterations). Target was >= 950.
- Learning curve progression: 232 → 348 → 562 → 842 → 968 → 988 → 995

### Diagnosed a 184s/iteration bottleneck
- Training was painfully slow. GPU at 0%. Initial suspicion: JIT retracing in `value_and_grad`.
- Created `diagnose_speed.py` to isolate each operation. Found the real culprit: `env.step` taking 2.8s/call without `jax.jit` wrapping (MJX dispatches ~200 physics primitives eagerly).
- **Fix:** `env_step = jax.jit(env.step)` — one line, 600x speedup (184s → 0.3s per iteration).
- Lesson: profile first, optimize second. The bottleneck was not where we thought.

### Benchmarked three PPO implementations
Created `ppo_scan.py` with `jax.lax.scan` for the epoch/minibatch loops, then benchmarked all three Linen versions:

| Version | `update()` per call | vs eager |
|---|---:|---:|
| `ppo.py` — Python loops, no JIT | 2.712s | 1x |
| `ppo_jit.py` — JIT closures, Python loops | 0.089s | 30x |
| `ppo_scan.py` — fully compiled with scan | 0.005s | 542x |

The jit→scan jump (18x) was larger than expected. For small MLPs, ~95% of each minibatch step call was Python↔XLA dispatch overhead, not gradient compute.

### Updated train.py to use ppo_scan
Switched import from `ppo_jit` to `ppo_scan` as the production version.

## Key learnings
- `jax.jit(env.step)` is mandatory for MJX envs called from Python loops
- `jax.block_until_ready()` is required for accurate JAX timing (async dispatch)
- `jax.lax.scan` eliminates Python dispatch overhead — matters even for tiny networks
- Truncation != termination: `effective_done = done * (1 - truncation)` for correct GAE bootstrapping
