## HP Tuning Agent — Design Brainstorm

Brainstormed and specced an autonomous HP tuning agent. Implementation deferred — spec is ready when needed.

### Core concept
Claude Code session as a file-based state machine. All state lives in a tuning log (`.context/tuning/<session>.md`). Each iteration: read log → poll wandb → diagnose → write decision → act → sleep. Context stays minimal because the log IS the memory, not the conversation.

### Key design decisions
- **Hybrid diagnostics:** rule-based heuristics for known failures (entropy collapse, Q divergence, etc.), LLM reasoning escalation for novel situations
- **Two modes:** autonomous (tier 1-2 HPs, runs until budget/target/plateau) and collaborative (tier 3 reward shaping, human in the loop)
- **Sequential runs with GPU gating** — one run at a time on the RTX 5080, agent checks nvidia-smi before launching
- **Context optimization** — poll via wandb API (not stdout), tuning log as single source of truth, sleep between polls
- **Stopping conditions:** first of (target reached, budget exhausted, plateau detected, human interrupt)

### Diagnostic rules defined
ENTROPY_COLLAPSE, Q_DIVERGENCE, Q_UNDERFIT, REWARD_PLATEAU, SLOW_CONVERGENCE, SPS_DEGRADING, TRAINING_DIVERGED, NAN_DETECTED, ALPHA_COLLAPSE, OOM_CRASH

### Prerequisites for implementation
- Add 5 CLI flags to `train_offpolicy.py`: `--alpha-init`, `--tau`, `--gamma`, `--hidden-dim`, `--policy-delay`
- Note: `--gamma` routes to TrainConfig (shared), not algo config

### Separate deploy venv (Python 3.12)
CycloneDDS 0.10.x has a C extension incompatible with Python 3.13 (`_Py_IsFinalizing` symbol change). Solution: separate venv.

- **Training**: `.venv/` — Python 3.13, JAX/MJX/Flax, managed by root `pyproject.toml`
- **Deploy**: `deploy/.venv/` — Python 3.12, numpy/cyclonedds/unitree_sdk2, managed by `deploy/pyproject.toml`
- Setup script: `bash deploy/setup_deploy_deps.sh` (builds CycloneDDS, installs SDK, clones simulator)
- Verified: both venvs work, zero contamination

### Key discovery: CycloneDDS + Python 3.13 incompatibility
`cyclonedds==0.10.5` builds a C extension (`_clayer.cpython-313-*.so`) that references `_Py_IsFinalizing` — this symbol was changed in Python 3.13. The cyclonedds-python repo hasn't been updated for 3.13 yet. The fix is using Python 3.12 for deploy, which is fine since deploy code is pure numpy anyway.

- **Task 4:** `robot_interface.py` — Go2Interface wraps CycloneDDS pub/sub. `get_state()` → joint pos/vel + IMU. `send_action()` remaps policy→SDK order, computes q_targets, writes with CRC.
- **Task 5:** `deploy_go2.py` — CLI with `--sim`/`--interface`, FSM (idle→stand→hold→policy), 50Hz loop, auto sys.path for deploy venv.

## MJCF Comparison: Why Sim2Sim Failed

Dispatched 3 parallel agents to probe both Go2 models. Found the full diff.

### The killer differences

1. **Actuator model** — Our env: `general` actuator with PD baked in (`gainprm=35, biasprm=[0,-35,-0.5]`). Policy outputs position targets, MuJoCo applies PD internally per-substep. unitree_mujoco: `motor` actuator (pure torque, gain=1). DDS bridge computes PD externally at 50Hz. Same math, different integration timing.

2. **Joint damping 5x** — Training: `dof_damping=0.5` (overridden in go2_base.py). unitree_mujoco: `0.1` (XML default). Higher damping = more stable but slower. Policy trained with 0.5 overshoots violently in 0.1.

3. **Contact model** — Training: condim=3 (basic friction), pyramidal cone, friction=[0.6, 0.005, 0.0001]. unitree_mujoco: condim=6 (full 3D), elliptic cone, friction=[0.4, 0.02, 0.01].

4. **Rear thigh range** — Training uses front thigh range for all legs [-1.5708, 3.4907]. unitree_mujoco has asymmetric rear [-0.5236, 4.5379].

### What matches
- Keyframe pose: identical (`[0, 0.9, -1.8]*4`, height 0.27m)
- Joint names, mesh geometry, gravity, armature, frictionloss
- Actuator ordering difference already handled by deploy remapping

### Next steps
Option A (recommended): Modify go2_base.py overrides to match unitree_mujoco physics, retrain. This aligns training with the model closest to real hardware.

Full comparison: `.context/go2/mjcf_comparison.md`

## Sim2Sim Round 2: Trajectory Analysis

Retrained PPO with Kd=0.1 (eval 219 at 12M steps, plateauing). Ran sim2sim with trajectory logging.

### Results
- Robot stands up (0.296m) — FSM works
- Robot explodes when policy takes over — joint velocities spike to ±95 rad/s
- Training distribution for jvel: ±5 rad/s. Deploy sees 19x that.
- Gyro also 13x out of range (±40 vs ±3)
- Feedback loop: bad obs → bad action → worse obs → worse action

### Root cause
PD integration timing. Training: PD applied per physics substep (every 0.004s, 5× per control step). Deploy: PD computed externally at 50Hz, constant torque held for 4 substeps. Joints accelerate freely between updates. Same gains, completely different transient dynamics.

### Fix options (prioritized)
1. **500Hz PD loop** — keep policy at 50Hz, run PD servo at 500Hz in separate thread (matches real robot)
2. **Clip obs velocities** — band-aid, prevents feedback loop
3. **Retrain with torque actuators** — match deploy model, most correct long-term

The Kd matching was necessary but not sufficient. The actuator TYPE is the real parity issue.

### Round 3: Direct PD (no DDS)

Wrote `sim2sim_direct.py` — bypasses DDS entirely, runs PD at physics rate (every mj_step) matching unitree_rl_gym's `deploy_mujoco.py` pattern.

**Still fails.** jvel hits ±65 even with PD per physics step. The very first action (step 1) overshoots to jvel_max=14.8. PD rate was NOT the root cause.

**Root cause confirmed:** `general` actuator (biastype="affine") produces fundamentally different dynamics than `motor` actuator + external PD, even with same Kp/Kd at same rate. Every other Go2 RL pipeline (unitree_rl_gym, unitree_rl_lab, walk-these-ways) uses `motor` + external PD. Our training env is the outlier.

**Next step:** Switch training env from `general` to `motor` actuators with external PD. This is the actual hardware parity fix. Everything else was symptoms.

### Round 4: Motor actuators + external PD retrain

Switched go2_base.py from `general` (biastype=affine) to `motor` (gain=1, no bias) with external PD in step(). PD computed per substep via lax.scan. Full 50M PPO run: **eval 244.6** (better than old general actuator 233).

Sim2sim with direct PD: **still fails.** Robot stands briefly (z=0.218 at step 50) then falls. jvel ±72 in deploy vs ±55 in training (2.5x std difference: 13.6 vs 5.4).

**Remaining gap:** Contact physics. Our training uses condim=3, pyramidal cone, friction=[0.6, 0.005, 0.0001]. unitree_mujoco uses condim=6, elliptic cone, friction=[0.4, 0.02, 0.01]. Also we zeroed dof_damping in training (PD handles it) but unitree_mujoco has 0.1.

**Status:** Actuator model is matched. Contact physics and joint damping are the remaining differences. Options: match contacts too, or domain rand.

### Round 5: Domain Randomization

Implemented `go2_randomize.py` — adapted Playground Go1 pattern. Randomizes: floor friction U(0.3,1.2), body mass ×U(0.9,1.1), torso payload +U(-1,3)kg, COM jitter, armature, frictionloss, initial joint pos. Wired via `--domain-rand` flag + `BraxDomainRandomizationVmapWrapper`.

Full 50M PPO + DR: **eval 237** (peak 241 ±12). Slightly lower than no-DR (244) — expected.

Sim2sim: still falls. DR covered friction value range but not the friction MODEL (condim 3 vs 6, pyramidal vs elliptic).

### Round 6: Full physics match in sim2sim

Matched EVERYTHING in sim2sim_direct.py: contacts (condim=3, friction=[0.6,...], solimp=[0.9,...]), friction cone (pyramidal), physics dt (0.004, 5 substeps). Still falls at step ~100.

**Conclusion:** The gap isn't any single parameter — it's the MJCF model itself. Menagerie `go2_mjx.xml` and unitree_mujoco `go2.xml` have different body inertias, mesh geometry, joint configurations beyond what we can override at runtime. The real fix: train directly on the unitree_mujoco model, or port their model to MJX.

### Round 7: Full XML audit — the actual root cause

Read both MJCFs line by line instead of running more numerical experiments.

**Damping was 2.0 in Menagerie, 0.1 in unitree_mujoco. 20x difference. One XML attribute.**

Everything else is identical (body positions, meshes, IMU, joint names). Sensor ordering differs but our remapping was correct all along. The "fundamentally different models" were the same model with different default joint damping.

Verified by stepping both models with matched damping — velocities align. Verified sensor mapping by comparing `jointpos joint="..."` attributes — both read same physical joints.

**Full diff (from XML):**
1. damping: 2.0 vs 0.1 (FIXED in go2_base.py → 0.1)
2. frictionloss: 0 vs 0.2 (FIXED → 0.2)
3. actuator type: general vs motor (FIXED → motor + external PD)
4. contacts: condim 3 vs 6 (left for DR)
5. sensors: correct remapping ✅
6. bodies/meshes: identical ✅

Retraining with all fixes (seed 6000) running.
