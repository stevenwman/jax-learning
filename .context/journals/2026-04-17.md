## Key Redesigns Mid-Implementation

### Menu trim: 8 → 4 terrain types

Original plan: Flat, Rough, Slope, PyramidStairs, InvertedPyramidStairs, Obstacles, SteppingStones, TiltedGrid.

**Flat** dropped: redundant with `Go2WarpJoystickFlat`. **Slope** dropped: attempted alternating hills, but varying tilt magnitude across rows created flat spots at row transitions regardless of how the alternation was structured. Problem is inherent to fixed tile width + variable height — can't be tuned away without ragged tile edges. Dropped entirely rather than ship a broken primitive. **Obstacles/SteppingStones** dropped: deployment relevance unclear, curriculum signal definition non-obvious. Kept the 4 that cleanly cover distinct locomotion challenges.

### Inverted pyramid: visually identical to pyramid → fixed to actual bowl

Initial implementation: `InvertedPyramidStairs = PyramidStairs with z-negated`. When rendered, both look identical because the pit is hidden below the ground plane. Fixed by constructing from scratch: rim at z=0, descending rings inward. Robot enters at the rim elevation and must handle descending terrain. Mechanically distinct from up-pyramid.

### Slope: alternating + overhang variants both had flat spots

Tried two implementations:
1. Alternating tilt direction (up row, down row, up row…) — transition at boundaries is a flat strip.
2. Single-direction slope with overhang at far end — creates a visible seam.

Both fail for the same reason: tilt magnitude increases with row index (harder = steeper) but tile width is fixed. The height delta at the row boundary doesn't match. Concluded slope needs variable tile width or height matching logic that's out of scope. Dropped from Phase 1.

### Tile size 8m → 9.6m

8m tiles were borderline for episode length. At 1.5 m/s for 20s, robot travels 30m — crosses 3-4 tiles. 9.6m gives 4.8m margin per direction from tile center; combined with goal-directed commands pulling toward tile interior, boundary crossing becomes rare.

### Command scheme: Bernoulli random → goal-directed P-controller

`WarpJoystick.step()` runs a Bernoulli sampler that resamples velocity commands mid-episode. This works fine for flat terrain but undermines curriculum: robot can advance by random walk rather than directed navigation. New scheme: fixed world-frame goal per episode, per-step command from `(goal_pos - robot_pos)` angle + distance. Robot must consistently navigate toward goal to advance.

**Critical gotcha discovered:** `WarpJoystick.step()` also overwrites `state.info["command"]` after physics. Goal-directed command must be injected both BEFORE super().step() (so physics uses the right command for reward computation) and AFTER (so obs reflects the right command, not the clobbered Bernoulli value). First implementation only injected before — obs had wrong command values during training. Fixed with pre+post injection pattern.

### Curriculum signal: tracking reward mean → binary reach/fall outcome

Reward mean requires per-episode buffering and varies across terrain types. Binary outcome (reached_goal OR fallen) is simpler, terrain-agnostic, and directly tests the capability we care about. Implemented as episode accumulators in `state.info`.

## Known Issues

### Eval OOM on curriculum env

`final_eval_and_checkpoint` instantiates a second eval env. On curriculum env (~1500 geoms), two Warp graphs at 16GB = OOM. Workaround: `XLA_PYTHON_CLIENT_PREALLOCATE=false` or skip final eval. Not blocking for training; blocking for eval metrics.

### Per-terrain VRAM scaling

Training with 64 envs is sustainable. Going higher (128+) OOMs. If faster throughput is needed, options: (a) reduce terrain grid (fewer rows), (b) reduce tile geom density in primitives, (c) larger GPU.

### Gotcha: `njmax` bump causes OOM

Initial instinct on "nefc overflow — please increase njmax to 123" warning was to bump `njmax=256, naconmax=8*8192` in curriculum `default_config()`. Caused Warp forward-pass OOM (24MB alloc fail inside solver kernel). Reverted to defaults (njmax=100, naconmax=32768). Warning is cosmetic — sim functions correctly at defaults. ### Gotcha: Warp kernel cache accumulates across in-process env creation

Running stress-test probes in sequence within one `python` process hit `Warp CUDA error 2: out of memory (wp_cuda_graph_create_exec)` on the 3rd probe onward. Cause: each env instantiation + first-step triggers new Warp graph captures that aren't reclaimed. Workaround for testing: run each probe in a fresh subprocess. For training this is a non-issue (one env for the run).

## PM Session (2) — Env Audit + Major Redesign Found Mid-Way

Three real bugs emerged from video inspection before kicking off the 20M run:

**Bug 1 — `_terrain_origins` stored primitive spawn-offset, not tile center.**

Generator wrote `origins[r,c] = [so[0]+tile_x, so[1]+tile_y, so[2]]` where `so` was the primitive's spawn_origin (e.g., `(0, sy*0.45, 0.3)` for pyramid = +y edge). Curriculum env then used `tile_origin[:2]` as both spawn anchor AND goal anchor. Net: goal_world = tile's +y EDGE = tile-to-tile boundary instead of tile center. Red goal marker visible "between two pyramids" in recording.

Fix: `origins[r,c] = [tile_x, tile_y, 0]` — pure tile center. Callers add tile-local offsets explicitly.

**Bug 2 — command scheme was unicycle, not holonomic.**

Old scheme:
```
cmd_vx = target_speed    # always body-forward
cmd_vy = 0
cmd_yaw_rate = P * yaw_error
```
Robot had to turn before walking toward goal. During visual review, green body-cmd arrow stayed pointing at robot's current facing direction, not at goal, because robot couldn't turn fast enough.

Fix: holonomic decomposition from world-frame goal direction:
```
world_vel = unit(goal - robot) * target_speed
cmd_vx =  cos(yaw)*world_vx + sin(yaw)*world_vy
cmd_vy = -sin(yaw)*world_vx + cos(yaw)*world_vy
cmd_yaw_rate = parent's Bernoulli sample (untouched — serves as DR)
```
Robot now side-steps toward goal regardless of heading.

**Bug 3 — single-class scheme wrong for rough/tilted.**

Previous scheme treated all 4 terrain types identically (edge-to-edge traversal with goal reach). But rough and tilted aren't navigation tasks — they're locomotion-robustness tasks. "Reach this specific point" is artificial; deployment doesn't care about point-precision, only "walk stably in any commanded direction."

Split into two classes:
- **Class A (rough, tilted):** spawn at tile center with small jitter, random Bernoulli linvel (no override), promote = upright + ≥ 2m traveled, demote = fell or didn't move.
- **Class B (pyramid up/down):** spawn at rim, goal at tile center, holonomic linvel toward goal, promote = reached within 0.5m, demote = fell or no progress.

Gated via `_IS_GOAL_DIRECTED = (False, True, True, False)` indexed on terrain_type. Both env step and wrapper advancement logic use this.

New state.info fields: `spawn_xy`, `episode_max_dist_from_spawn` (for class-A advancement).

**Verification approach**

Added `tools/render_curriculum_spawns.py` — one topdown + iso PNG with green/red spheres for all 40 (level, type) tiles at once. Class A tiles show only green (goal overlaps spawn). Class B tiles show both. Catches placement bugs at a glance.

# PM Session — Push-T Manipulation Benchmark (Shape-Agnostic)

## Summary

Built a planar push benchmark in MuJoCo Warp. Design goal: train on push-T, test transfer to push-circle / push-L / push-plus to measure algorithm *adaptability* (not just T-specific performance). Obs space is shape-agnostic (block center + angle, not keypoints), same obs for every shape, so differences must come from contact dynamics inference.

## What Shipped

- **`jax_rl/envs/manipulation/push_env.py`** (single file, ~300 LOC): `PushEnv` MjxEnv subclass + `SHAPES` registry + XML template builder.
- **4 shapes wired:** T, L, circle, plus. Adding a new shape = one entry in `SHAPES` dict.
- **3 action modes:** `position` (PD target, jittery default), `velocity` (delta per step, smooth RL), `teleport` (gym-pusht speed-capped, demo-literature parity).
- **16d shape-agnostic obs:** `[pusher_xy, block_xy, sin/cos(yaw), target_xy, sin/cos(goal_yaw), pusher_vel, block_vel, last_action]`.
- **Reward:** dense `-pos_error - 0.3 * angle_error + 5.0 * success_bonus` (with sparse option). Success = pos < 2cm AND angle < 0.15 rad.
- **Randomized block + target pose per episode** (flags: `randomize_block`, `randomize_target`).

## Throughput

On MJX Warp, 1024 envs: **361,048 sps** for the push-T env. 28x faster than Go2WarpJoystickFlat at same env count. Cheap to experiment with.

## Design Decisions

### Why shape-agnostic obs (center + angle), not keypoints
Benchmark goal = test whether policy learned *pushing physics* vs T-geometry memorization. Keypoints leak shape identity (T has 4 corners, plus has 8). Center + sin/cos(yaw) = same 4 obs dims regardless of shape. Policy has to infer contact dynamics from block response.

### Why 3 action modes
- **position-PD** (kp=80): matches our locomotion convention, lets same training code work.
- **velocity/delta**: RL-native, small action per step, smooth.
- **teleport** (speed-capped, 0.25 m/s): matches gym-pusht for Diffusion Policy baselines.

All three share the same obs and reward — only `ctrl` computation differs. Ablation isolates action parameterization vs dynamics.

### Why programmatic XML instead of per-shape files
Template has shared structure (pusher, walls, lights, target ghost). Shape-specific geoms injected via `_build_geom_xml`. Target ghost mirrors the same geom spec (transparent, `contype=0`). Adding a shape = one dict entry in `SHAPES`.

## Bugs Found and Fixed

### 1. `mjx.put_model(impl="jax")` crashes on cylinder-box
`NotImplementedError: (CYLINDER, BOX) collisions not implemented.` MJX JAX backend doesn't handle this narrowphase. Pusher=cylinder + block=box → Warp-only. Lesson documented.

### 2. Default contact too soft → visible penetration
Default `solref="0.02 1"` = 20ms ≈ 10 sim steps to resolve. Fixed: `solref="0.004 1" solimp="0.98 0.995 ..."` + `iterations=50 ls_iterations=10`.

### 3. Default MuJoCo lights too bright
Added `<visual><headlight ...>` override, floor `reflectance=0 specular=0`. Darker, flatter — better for video analysis.
