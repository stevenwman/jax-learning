### Key findings from Brax PPO comparison
Read the full Brax PPO source (`brax/training/agents/ppo/losses.py` and `train.py`) and found critical structural differences:

1. **Batch size mismatch**: Brax collects `batch_size × num_minibatches × unroll_length = 1024 × 32 × 30 = 983,040` samples per training step (16 separate rollout segments). We collected only `2048 × 30 = 61,440` (one segment). **16x less data** with the same number of gradient steps.

2. **Minibatch size**: Brax uses ~30,720 samples per minibatch (983k / 32). We used 2,048. **15x smaller** → much noisier gradients.

3. **clip_eps**: Brax default is 0.3, we used 0.2. Tighter clipping → higher clip fraction.

4. **Advantage normalization**: Brax normalizes over entire batch before splitting into minibatches. We normalized per-minibatch (noisier statistics).

5. **Gradient steps**: When we "fixed" batch size by increasing num_steps to 480, we got 983k samples but minibatch_size stayed at 2048 → `480 minibatches × 16 epochs = 7,680 gradient steps` instead of Brax's `32 × 16 = 512`.

### Pipeline audit — making it plug-and-play
Audited the entire training pipeline for env-specific assumptions:

**Fixed:**
- **Crash bug**: `obs[perm].reshape(num_minibatches, minibatch_size, -1)` would crash for any env where `samples_per_iter` wasn't divisible by `minibatch_size`. Added truncation.
- **Hardcoded minibatch formula**: Replaced `min(2048, samples_per_iter)` with `samples_per_iter // ppo_cfg.num_minibatches`. Added `num_minibatches: int = 32` to PPOConfig.
- **PPOConfig defaults**: `minibatch_size` and `num_envs` were always overridden by train.py. Defaults now `0` (clearly "runtime-computed").
- **clip_eps default**: Changed from 0.2 to 0.3 to match Brax.
- **Advantage normalization**: Moved from per-minibatch to batch-level (before epoch loop), matching Brax.
- **Episode tracking**: Replaced Python `for i in range(num_envs)` loop with vectorized numpy boolean indexing. Was 983k Python iterations per rollout for HumanoidRun.

### Interleaved collect→update (num_updates_per_batch)

Initially misread Brax's `num_updates_per_batch` as "sequential collect→update cycles." It actually means **epochs** (passes over the same batch). Our implementation of the inner loop was based on a wrong interpretation. Setting `num_updates_per_batch=1` disables the inner loop (default). The feature is still in the codebase as a generalization.

Added checkpoint saving every 5 iterations (overwriting same dir) and `--resume` flag for training resumption from checkpoint.

### Truncation bootstrap bug (CRITICAL)

**The bug:** When an episode truncates (timeout at episode_length), `wrap_for_brax_training` auto-resets the env. `env_state.obs` becomes the reset observation. Our GAE used `V(reset_obs)` as the bootstrap value for truncated transitions — but the humanoid was in a completely different state (running vs standing still). This systematically undervalued good trajectories.

**First fix attempt (reward adjustment):** Added `gamma * V(s_t) * truncation` to the reward at truncation steps. This created massive reward spikes at synchronized episode boundaries → NaN at iter 9.

**Working fix (GAE-level):** In `compute_gae`, when `truncation[t]=1`, replace `next_values[t]` with `values[t]` (approximate V(truncated_state) ≈ V(current_state)). No reward modification. Uses `effective_done = done * (1 - truncation)` so GAE bootstraps through truncations with the corrected value.

This is likely the primary cause of poor HumanoidRun performance across all runs — value estimates were corrupted at every episode boundary.

## Key learnings
- **Truncation bootstrap matters hugely.** With auto-reset envs, V(reset_obs) ≠ V(truncated_obs). Using the wrong one systematically corrupts value estimates. Fix in GAE, not reward adjustment (reward spikes cause instability).
- **Minibatch count, not size, is the right parameterization.** Brax uses `num_minibatches=32` as the primary knob. Fixing minibatch_size leads to wildly different gradient step counts as data volume changes.
- **Batch size and gradient steps are coupled.** Increasing data (num_steps) without adjusting minibatches/epochs gives proportionally more gradient steps → overfitting.
- **Policy collapse = overtraining signal.** Entropy dropping to negative values, clip fraction → 0, KL → 0 means the policy stopped exploring. Usually caused by too many gradient steps relative to data.
- **Reference implementation comparison is essential** for high-dim control. CheetahRun (6 action dims) was forgiving of these issues. HumanoidRun (21 action dims) exposed them all.
- **Diagnostics (log_std stats) were invaluable** for distinguishing between HP issues and bugs.
- **Read the source, don't guess at parameterization.** Misread Brax's `num_updates_per_batch` as inner collect→update loops when it actually means epochs. Cost several failed runs.
