### Key findings from Brax PPO comparison
Read the full Brax PPO source (`brax/training/agents/ppo/losses.py` and `train.py`) and found critical structural differences:

1. **Batch size mismatch**: Brax collects `batch_size × num_minibatches × unroll_length = 1024 × 32 × 30 = 983,040` samples per training step (16 separate rollout segments). We collected only `2048 × 30 = 61,440` (one segment). **16x less data** with the same number of gradient steps.

2. **Minibatch size**: Brax uses ~30,720 samples per minibatch (983k / 32). We used 2,048. **15x smaller** → much noisier gradients.

3. **clip_eps**: Brax default is 0.3, we used 0.2. Tighter clipping → higher clip fraction.

4. **Advantage normalization**: Brax normalizes over entire batch before splitting into minibatches. We normalized per-minibatch (noisier statistics).

5. **Gradient steps**: When we "fixed" batch size by increasing num_steps to 480, we got 983k samples but minibatch_size stayed at 2048 → `480 minibatches × 16 epochs = 7,680 gradient steps` instead of Brax's `32 × 16 = 512`.

### Pipeline audit — making it plug-and-play
Audited the entire training pipeline for env-specific assumptions:

**Fixed:**
- **Crash bug**: `obs[perm].reshape(num_minibatches, minibatch_size, -1)` would crash for any env where `samples_per_iter` wasn't divisible by `minibatch_size`. Added truncation.
- **Hardcoded minibatch formula**: Replaced `min(2048, samples_per_iter)` with `samples_per_iter // ppo_cfg.num_minibatches`. Added `num_minibatches: int = 32` to PPOConfig.
- **PPOConfig defaults**: `minibatch_size` and `num_envs` were always overridden by train.py. Defaults now `0` (clearly "runtime-computed").
- **clip_eps default**: Changed from 0.2 to 0.3 to match Brax.
- **Advantage normalization**: Moved from per-minibatch to batch-level (before epoch loop), matching Brax.
- **Episode tracking**: Replaced Python `for i in range(num_envs)` loop with vectorized numpy boolean indexing. Was 983k Python iterations per rollout for HumanoidRun.

### Interleaved collect→update (num_updates_per_batch)

Initially misread Brax's `num_updates_per_batch` as "sequential collect→update cycles." It actually means **epochs** (passes over the same batch). Our implementation of the inner loop was based on a wrong interpretation. Setting `num_updates_per_batch=1` disables the inner loop (default). The feature is still in the codebase as a generalization.

Added checkpoint saving every 5 iterations (overwriting same dir) and `--resume` flag for training resumption from checkpoint.

### Truncation bootstrap bug (CRITICAL)

**The bug:** When an episode truncates (timeout at episode_length), `wrap_for_brax_training` auto-resets the env. `env_state.obs` becomes the reset observation. Our GAE used `V(reset_obs)` as the bootstrap value for truncated transitions — but the humanoid was in a completely different state (running vs standing still). This systematically undervalued good trajectories.

**First fix attempt (reward adjustment):** Added `gamma * V(s_t) * truncation` to the reward at truncation steps. This created massive reward spikes at synchronized episode boundaries → NaN at iter 9.

**Working fix (GAE-level):** In `compute_gae`, when `truncation[t]=1`, replace `next_values[t]` with `values[t]` (approximate V(truncated_state) ≈ V(current_state)). No reward modification. Uses `effective_done = done * (1 - truncation)` so GAE bootstraps through truncations with the corrected value.

This is likely the primary cause of poor HumanoidRun performance across all runs — value estimates were corrupted at every episode boundary.

## Key learnings
- **Truncation bootstrap matters hugely.** With auto-reset envs, V(reset_obs) ≠ V(truncated_obs). Using the wrong one systematically corrupts value estimates. Fix in GAE, not reward adjustment (reward spikes cause instability).
- **Minibatch count, not size, is the right parameterization.** Brax uses `num_minibatches=32` as the primary knob. Fixing minibatch_size leads to wildly different gradient step counts as data volume changes.
- **Batch size and gradient steps are coupled.** Increasing data (num_steps) without adjusting minibatches/epochs gives proportionally more gradient steps → overfitting.
- **Policy collapse = overtraining signal.** Entropy dropping to negative values, clip fraction → 0, KL → 0 means the policy stopped exploring. Usually caused by too many gradient steps relative to data.
- **Reference implementation comparison is essential** for high-dim control. CheetahRun (6 action dims) was forgiving of these issues. HumanoidRun (21 action dims) exposed them all.
- **Diagnostics (log_std stats) were invaluable** for distinguishing between HP issues and bugs.
- **Read the source, don't guess at parameterization.** Misread Brax's `num_updates_per_batch` as inner collect→update loops when it actually means epochs. Cost several failed runs.

### HumanoidRun preset fix — applied Session 5 lessons

Preset still had the old config (`num_steps=480, num_updates_per_batch=1, num_epochs=4`) despite Session 5 documenting the fix. This caused the same NaN blowup pattern:

### Run 12: Matching actual Brax reference config

Discovered `num_updates_per_batch` in Brax means epochs (multiple SGD passes over same batch), NOT interleaved collect→update cycles. Brax docstring: "the number of times to run the gradient update over all minibatches **before doing a new environment rollout**."

Our interleaved setup (16 fresh collections × 1 epoch) was doing 16× more collection with 16× fewer gradient updates per batch. Policy barely trained on each chunk before throwing it away → flat returns (~4.4 at 25M steps).

Run 12 config (matching Brax/Playground reference):
- `num_envs=2048, num_steps=30, num_epochs=16, num_updates_per_batch=1`
- `gamma=0.995, entropy_coef=1e-2, policy_hidden_dim=(128,)×4`
- `minibatch_size = (2048 * 30) / 32 = 1920`

**Known risk:** Brax's `batch_size=1024` parameter multiplies collection volume (total samples = batch_size × num_minibatches × unroll_length = 1024 × 32 × 30 = 983k). We collect `2048 × 30 = 61k`. Our minibatch_size (1920) is much smaller than Brax's (~30k). If this run fails with high clip fraction / KL spikes, batch size mismatch is the likely cause.

**Result:** Entropy exploded (30→71), log_std hit clip max at 2.0, clip fraction 1.0. Batch too small (61k vs Brax's 983k) for 16 epochs.

### Brax parity audit

Full comparison of our PPO vs Brax PPO revealed structural differences beyond just hyperparameters:

| Difference | Impact |
|-----------|--------|
| Data volume (61k vs 983k samples/iter) | HIGH — 16 epochs on 61k = massive overtraining |
| Entropy computation (raw Gaussian vs tanh-corrected) | HIGH — raw entropy 30+ nats, actual tanh entropy ~14 |
| Tanh squashing (Brax default) vs no squash + hard clip | HIGH — different policy distribution |
| Per-minibatch GAE recomputation (Brax) vs once (ours) | MEDIUM-HIGH |
| LR annealing (ours) vs constant LR (Brax) | MEDIUM |
| Advantage normalization scope (batch vs per-minibatch) | MEDIUM |
| Kernel init: lecun_normal (ours) vs lecun_uniform (Brax) | LOW-MEDIUM |
| Separate vs joint optimizer | LOW-MEDIUM |

### Run 13: Correct batch size, no squash, entropy=0

Fixed batch volume by setting `num_steps=480` (2048 × 480 = 983k, matching Brax). With `anneal_lr=False`, `entropy_coef=0`. Entropy decreased steadily (29→18) but returns still flat (~4.4 at 25M steps). Stable but slow — same pattern as earlier non-matching runs.

### Run 14: Tanh squash + raw entropy (broken)

Enabled `squash=True` to match Brax's `tanh_normal`. Immediate blowup: `entropy_gaussian` still computed raw Gaussian entropy (30+ nats) instead of tanh-corrected entropy (~14 nats). The `entropy_coef=1e-2` bonus on inflated entropy dominated task reward → log_std rammed to clip max (2.0), KL 296k, clip fraction 1.0.

**Lesson:** When switching to tanh-squashed actions, the entropy computation MUST account for the tanh Jacobian. Raw Gaussian entropy is meaningless for the squashed distribution.

### Run 15: Full Brax parity fixes — first stable training

Applied all parity fixes simultaneously:
1. **Tanh squashing** (`squash=True`) — configurable via `TrainConfig.squash`
2. **Tanh-corrected entropy** — single-sample estimate: `-E[log p(tanh(x))]` with Jacobian correction, matching Brax
3. **Per-minibatch advantage normalization** — moved from batch-level to inside `_minibatch_step`
4. **lecun_uniform kernel init** — all Dense layers in encoder, gaussian head, value head
5. **Correct batch size** — `num_steps=480`, giving 983k samples/iter
6. **Constant LR** — `anneal_lr=False`
7. **entropy_coef=1e-2** — safe now with corrected entropy

**Result:** First fully stable 60M step run. Returns: 5.3 avg (max 9.7). All metrics healthy throughout — entropy steady at ~14, KL ~0.02, clip fraction ~0.1, log_std slowly decreasing from 0 to -0.2.

**Still far from Brax target (50-200).** Remaining structural gaps:
- GAE computed once vs recomputed per-minibatch (Brax re-evaluates V from current params each minibatch)
- State-dependent std (Brax's tanh_normal has network-predicted scale)

### Run 16: Per-epoch GAE recomputation + per-minibatch advantage norm

Applied the last structural parity fix — GAE is now recomputed from current critic params at the start of each epoch (inside `lax.scan` over epochs), matching Brax's approach. Also moved advantage normalization back to per-minibatch (matching Brax).

**Result:** Returns 6.9 avg (max 12.2) at 60M steps. Marginal improvement over run 15 (5.3 avg). All metrics healthy.

### Periodic VLoss spike pattern in WalkerWalk

Observed a recurring pattern every ~33 iterations throughout WalkerWalk training:

```
Iter 899: VLoss 0.82, Ent 1.457  ← normal
Iter 900: VLoss 14638.71, Ent -6.515  ← explosion
Iter 901: VLoss 6497.71, Ent -4.140
Iter 902: VLoss 3973.74, Ent -2.119
...
Iter 910: VLoss 19.87, Ent 1.389  ← recovered
```

**Root cause:** 2048 envs × episode_length 1000 / 30 steps per iter ≈ 33.3 iters per episode → all 2048 envs reset simultaneously every ~33 iterations. At reset, the value function sees a completely different state distribution than mid-episode. The VLoss spike is the critic fitting to this distribution shift. Entropy going to -6.5 is a tanh-squashing artifact: when std briefly collapses after a large gradient step, `log_prob` of the sample can go positive → `-log_prob` (entropy estimate) goes negative.

**Key observation:** Self-correcting within ~5 iterations and didn't prevent convergence (final return 833). But this is the same synchronized-reset instability documented in Session 5, now manifesting as periodic spikes rather than alternating VLoss oscillation.

**This would be fixed by** `num_updates_per_batch=16, num_steps=20` (Brax's interleaved config), which desynchronizes episode phases across update cycles. For WalkerWalk it wasn't severe enough to matter, but it explains why HumanoidRun NaN'd at these boundaries.

### Checkpoint infrastructure overhaul

**Problem:** `record_video.py` couldn't restore from checkpoints because orbax `StandardCheckpointer.restore()` requires exact pytree structure match between the checkpoint (saved with `optax.chain(clip_by_global_norm, adam)`) and the restore target (initialized with bare `optax.adam`). Produces a `ValueError` about mismatched `EmptyState` vs `dict`.

**Root cause analysis:** Orbax saves the full `TrainingState` including optimizer state. Any structural difference in the optimizer chain (bare adam vs chain) produces a type mismatch that orbax refuses to restore.

**Solutions tried and rejected:**
- `strict=False` — only for shape mismatches (array truncation/padding), not tree structure
- `partial_restore=True` — only on the lower-level `PyTreeRestore` API, not `StandardCheckpointer`
- Reconstructing the exact optimizer chain in record_video — brittle and requires knowing train-time config

**Final design:**
1. `train.py` saves `actor_params.npy` alongside the orbax checkpoint — a plain numpy dict containing only `actor_params`, `norm_mean`, `norm_mean_of_squares`, `norm_count`. No orbax, no optimizer state.
2. `record_video.py` loads from `actor_params.npy` directly — immune to optimizer structure changes.
3. `train.py` now stores the full `dataclasses.asdict(cfg)` in `meta.json` (under key `train_config`) instead of the hand-crafted subset. Self-documenting, self-sufficient for future resume.

**Lesson on checkpoint design:** Save inference artifacts separately from training artifacts. The orbax checkpoint is for resuming training (must include optimizer state). A separate `actor_params.npy` is for inference/video (needs only params + norm stats). These have different audiences and shouldn't be conflated.

**Bonus lesson — targetless orbax restore:** `ocp.StandardCheckpointer().restore(path)` without a `target` restores as a raw nested dict (with an UNSAFE warning). This is useful for extracting specific leaves from a checkpoint when you don't have the exact pytree structure.
