# 2026-03-21 — FastDSAC Rewrite + HumanoidRun Benchmarks

## What we did

### FastDSAC: Paper says "Gaussian NLL" but code uses Huber loss

Downloaded paper's source code via `gdown` from anonymous review link. Discovered the actual critic loss is **Huber-based** (delta=50) with bounded per-sample ratio weighting, NOT Gaussian NLL as the paper text implies.

Our Gaussian NLL implementation had unbounded `1/variance` that exploded at 32K batch. Rewrote `fast_dsac.py` to match the paper's actual loss.

**Key config differences found from source code:**
- `tau=0.1` (we had 0.005), `weight_decay=0.1` (we had 1e-4)
- `activation=gelu`, `reward_scale=0.2` (for HumanoidBench, not dm_control)
- `critic_hidden_dim=1024` (tapered 1024→512→256)
- `num_updates=2` per 128 envs = UTD needs 16 at 1024 envs

### FastDSAC Scaling Investigation (128 vs 1024 envs)

| Config | Envs | Buffer | Result |
|---|---|---|---|
| 51K buffer, 32K batch | 1024 | 51,200 | NaN at 2M (alpha collapse) |
| reward_scale=1.0 | 1024 | 51,200 | NaN at 2M (same) |
| UTD-matched (16 updates) | 1024 | 51,200 | NaN at 2M (same) |
| **Paper-matched** | **128** | 51,200 | **490 peak eval, no NaN** |
| **Scaled buffer** | **1024** | **409,600** | **316 eval, NaN at 53M** |

### Root cause of 53M NaN: `Inf` not `NaN`

Stress testing revealed: MJX produces `Inf` obs (velocity overflow), our guard only checked `isnan()`. `Inf` passes through, enters network, `Inf * 0 = NaN`.

- `obs = Inf` → algo NaN (confirmed)
- `obs = 1e6` → algo fine (confirmed)
- Fix: add `jnp.isinf()` to env step guard

## Key lessons

1. Always get the source code — paper text ≠ implementation
2. `Inf` and `NaN` are separate MJX failure modes, guard both
3. Buffer size must scale with env count (not just UTD)
4. Stress test edge cases directly instead of running full training
