The mental model (1 paragraph)

You train a Go2 policy in JAX on flat ground + an analytic "mud" force model (fast, GPU, jittable). You evaluate transfer on a separate Newton MPM granular-mud sim the policy never saw — that's the held-out test, and it has its own venv because Newton physics can't run inside jax.jit. Two worlds, two venvs. Training proves a recipe; Newton mud is the judge.

The controller idea (or nothing makes sense)

A Go2 variant picks one low-level controller from config. The policy's action means different things per controller:

ControllerWhat the action is
joint-PDjoint position targets (the normal thing)
OSC / variable-impedancefoot xyz targets + per-axis stiffness / damping (Cartesian impedance)
virtual-mass… + a commanded foot-acceleration term

The mud research finding in one line: variable-impedance penetrates mud deeper than joint-PD.

Run it (2 commands)

① Train (main venv, GPU)

# a known-good mud recipe (var-impedance + 4× mud DR + slow+firm reward)
# 'mud-slowfirm' is a short alias → Go2WarpOscVarDampingAxisFlatPhysicalMudDR4xSlowFirm
XLA_CLIENT_MEM_FRACTION=0.65 uv run python scripts/train_fast_sac.py \
  --env mud-slowfirm \
  --total-timesteps 5000000 --num-envs 256 --buffer-size 2097152 --wandb
# → checkpoints/<timestamp>_..._seed0/best

② Eval on Newton mud (separate venv, CPU actor + MPM)

# NEW: named flags (self-documenting). Run from the repo root.
WT=$(pwd)
JAX_PLATFORMS=cpu PYGLET_HEADLESS=1 PYTHONPATH=$WT \
  projects/mud_eval/.venv/bin/python projects/mud_eval/record_traverse_maxfwd.py \
  $WT/checkpoints/<run>/best \
  --frames 750 --spawn-y 3.3 --yaw -0.5 --controller osc --tag myeval
# metric: final base y on the thin→thick traverse.
#   LOWER = deeper = better.  y < 0 = cleared the whole mud gradient.
# bar to beat:  NoAir ≈ -2.4 (clears) · slow+firm ≈ -0.2 (clears)

(The old positional form … best 750 3.3 0.10 -0.5 myeval osc still works — but use the flags.)

Decode a variant name (systematic, not random)

The 55 envs are declared as data in jax_rl/envs/locomotion/go2_warp_variants.py — that table is the map of everything. A name is just its config knobs concatenated:

Go2Warp · Go2, Warp backend OscVarDampingAxis · var-impedance, per-axis K+D FlatPhysical · flat terrain, physical motor MudDR4x · 4× analytic-mud DR SlowFirm · reward profile

…which is precise but monstrous (up to 63 chars). So the ones you actually train have short aliases (in go2_warp_variants.py :: GO2_ENV_ALIASES) — --env mud-slowfirm resolves to the canonical name. The long names stay the source of truth; aliases are just handles.

AliasCanonical / what it is
flat-jointpdjoint-PD flat benchmark
flat-varimpvariable-impedance flat baseline
mud-slowfirmvar-imp + 4× mud DR + slow+firm — robust mud winner (clears)
mud-noair+ NoAir reward — deepest traverse
mud-massvirtual-mass controller on mud
mud-jointpdjoint-PD on mud (the control that bogs)

The 5 gotchas that will bite you

1 · Two venvs. uv run … for training; projects/mud_eval/.venv/bin/python … for eval. They don't share dependencies.
2 · A reward is a profile. All 17 terms always compute; a "reward" is just a reward_config.scales dict (scale 0 = off). SlowFirm / NoAir are scale dicts.
3 · Checkpoints self-describe their controller in meta["control"]["osc"]. The eval reads it — never hardcode controller params. A jax↔numpy parity test pins the two implementations equal.
4 · Spawn parity. The Newton eval starts the robot at the training home pose (0, 0.9, -1.8), base z 0.27. Mismatches here look like physics bugs (they're not).
5 · One GPU. Training and the Newton eval cannot run at the same time (16 GB). JAX_PLATFORMS=cpu on the eval is mandatory (the actor is CPU-bound by design; MPM keeps the GPU via Warp).

The 2-minute "does it work" loop

Train a known-good recipe → grab best/ → run the eval → read the final y. If y < 0, it cleared the mud. That's the whole feedback loop.
