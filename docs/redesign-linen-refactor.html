Repo Redesign — linen_refactor

How this repo would be built if we did it again. Goals & assumptions first, then the one rule that fixes the slop, then the moves — in ship order.

Thesis: the repo wants to be ManiSkill-shaped — a reusable algo library + a standardized env/benchmark suite + research that consumes both. The slop came from the dependency arrows pointing the wrong way: research bled into the library, the library bled into the algos. Fix the arrows and most of the convolution dissolves. Everything below serves that one correction.

Diagnosis — where the arrows broke

Bleed 1 · research → core

Mud variants are declared inside go2_warp_variants.py (a core env module). Core now knows MudDR4xSlowFirm exists. projects/mud_eval reaches into env internals (sensor adrs, controller math). Mud is a research project — it should import jax_rl; core should never name it.

Bleed 2 · env → algo

env_presets.py fuses algo hyperparameters with env-name defaults, so the algo library depends on which env strings exist. Backwards.
The loudest symptom — names like Go2WarpOscVarDampingAxisFlatPhysicalMudDR4xSlowFirmNoAirGaitBal (63 chars). You're naming points in a product space (base × controller × terrain × DR × command × reward) instead of constructing them. 55 frozen enums = combinatorial blow-up of a thing that wants to be a builder.

Target shape — 3 layers, one-way deps

projects/  (experiments)
mud, deploy-prep, sweeps. Imports the two below. Never imported by them. Owns its own DR/terrain/reward declarations.
▲ imports  │  may not be imported ▼
jax_rl/envs/  (tasks + plugin contracts)
Go2 base physics/obs/action, controller contract, terrain/DR hooks, a task registry. Knows nothing about "mud" or any experiment.
▲ imports  │  may not be imported ▼
jax_rl/algos/  (env-agnostic learners)
SAC / TD3 / FastSAC / FastTD3 / TDMPC2. Knows nothing about Go2, controllers, or env names.
enforce with ONE lint:  jax_rl/** may not import projects/**

That single rule, CI-enforced, prevents every future re-bleed. The layers above it are just the natural consequence of obeying it.

The moves (each ships independently)

1 · Controllers → first-class package strangler step 1

jax_rl/control/ with a contract: compute_tau(state, spec) -> tau. joint-PD / OSC / var-impedance / virtual-mass become peers, testable in isolation. Env takes a controller instance; research adds a new one from outside without touching go2_warp_base.py. Today they're tangled into the env step().

2 · Variants → builder, not enum

now

55 frozen names, up to 63 chars, in a core module.

target

a spec object that constructs the point in the product space:
make_go2(
  controller=VarImpedance(s=.., zeta=.., a=..),
  terrain=mud, dr="4x", command=slow_firm, reward=gait_bal)

Keep ~6 named presets for reproducibility; everything else is constructed. The short aliases added this session (mud-slowfirm → …) are already step one — a flat lookup over a space that wants real axes.

3 · One controller spec, two executors — kill the jax/numpy drift

The real tax: mud_osc.py (numpy, for Newton) duplicates the jax OSC. Every fix lands twice (the EMA bug, the stale print label). Target: the controller is a pure dataclass spec + a math kernel; the jax executor and the numpy executor both reconstruct from the same spec. The self-describing meta["control"]["osc"] we already emit is the seed — lean all the way in and a parity test becomes a first-class contract, not bespoke glue.

4 · Newton = an eval backend behind a protocol

Define EvalBackend (warp-train, newton-mpm-eval). Record/traverse scripts target the protocol, not "where the env hides its sensors." Separate venv stays (Newton can't run under jax.jit — correct call); we just give the seam a name instead of letting mud_eval reach through it.

5 · Presets split

algo_cfg (env-agnostic) and env_spec are different objects. An experiment pairs them and lives in the experiments layer. The library core stops depending on experiment wiring — undoes Bleed 2.

6 · Collapse the doc-sync matrix

The heavy CLAUDE.md doc-sync checklist (env → go2_constants.py → mjcf_comparison.md → env_presets → docs) exists because one fact lives in four places. Define gains/constants once, import everywhere; the cross-ref burden shrinks to near-zero.

Builder placement — the real sub-decisions

"Where does the builder live" isn't one question — it's five, and they're the load-bearing ones for move #2. The headline answer first, then the parts:

Builder machinery lives in core; the catalog is federated. make_go2(...) sits in jax_rl/envs/ and enumerates nothing — it takes typed axis plugins (controller, terrain, reward, DR). Generic axes (flat, rough, standard rewards) ship in core; experiment-specific axes (mud terrain, mud DR) live in projects/ and register their own named presets. That's how mud-slowfirm stays a real, resolvable name while core never says the word "mud."
Sub-decisionOptionsLean
Builder vs catalog — one module or two? (a) one file does both · (b) split: build.py = machinery, catalog = named points Two. Catalog stays readable as data; machinery stays testable.
Axis API — how does the builder take a terrain/controller? (a) strings terrain="mud" · (b) typed plugin objects terrain=Mud(...) Typed objects. Strings re-introduce a closed enum core must know → re-bleed. Objects keep core open: it calls terrain.apply(env), never names concretes.
Where do concrete axes live? (a) all in core · (b) generic in core, experiment-specific in projects/ Split. Flat/Rough/std rewards in core; MudTerrain/MudDR in projects/mud_eval. Obeys the one-way-dep rule by construction.
Catalog mechanism — how names register? (a) central dict literal · (b) @register decorator · (c) pyproject entry-points Decorator now (federated, each preset self-registers where defined). Entry-points later for library-grade external plugins.
String→env resolution (--env mud-slowfirm) — who owns it, lazy import? (a) eager global registry · (b) resolver merges core + experiment registries, experiment imported on demand Lazy-merged. A plain jax_rl user doesn't pay for mud; the CLI imports the experiment package only when its name is requested.

Concretely, the three files and who owns what:

# jax_rl/envs/go2/build.py    — CORE · open, enumerates nothing
def make_go2(*, controller: Controller, terrain: Terrain,
             reward: Reward, dr: DR, command: Command) -> EnvConfig: ...

# jax_rl/envs/go2/catalog.py  — CORE · generic named points only
@register("flat-jointpd")
def _(): return make_go2(controller=JointPD(), terrain=Flat(), ...)

# projects/mud_eval/envs.py   — EXPERIMENT · owns "mud", registers its own names
@register("mud-slowfirm")
def _(): return make_go2(controller=VarImpedance(...), terrain=Mud("4x"),
                         reward=SlowFirm(), ...)

The @register calls in projects/ only fire when that package is imported — so the dependency arrow stays projects → envs, never back. Mud is a Terrain the experiment defines; core's builder only ever sees the protocol.
