# Flow Policy Optimization (FPO) Port — Spec

**Date:** 2026-04-30
**Related papers:** [Flow Matching Policy Gradients (McAllister et al., 2025)](https://arxiv.org/abs/2507.21053), [Flow Policy Gradients for Robot Control (Yi et al., 2026)](https://arxiv.org/abs/2602.02481)
**Reference repos:** [akanazawa/fpo](https://github.com/akanazawa/fpo) (JAX, MuJoCo Playground), [amazon-far/fpo-control](https://github.com/amazon-far/fpo-control) (PyTorch, IsaacLab — FPO++ variant)
**Status:** Draft → Plan

---

## Problem

The repo's on-policy story is `jax_rl/algos/ppo.py` (Gaussian PPO with `lax.scan` update, asymmetric actor-critic, `tanh`-squash). It works, but Gaussian unimodality bottlenecks PPO on tasks where the optimal action distribution is multimodal — multimodal manipulation, motion-tracking with diverse demos, locomotion with multiple gait modes, exploration-heavy tasks. PPO papers often paper over this with auxiliary entropy bonuses or hand-tuned `log_std` schedules.

Flow Policy Optimization (FPO, McAllister 2025) replaces the Gaussian policy with a **flow-matching generative model** and replaces the `log π` ratio with a **conditional-flow-matching loss surrogate**:

```
ratio = exp(L_CFM_old(a, o) − L_CFM_new(a, o))
```

Cost per PPO update is **O(1)** in the number of ODE solver steps — the flow sampler runs as a black box during rollout, and only a single `(τ, ε)` pair (or a small N_mc batch) is replayed during the update. No BPTT through the sampler.

The follow-up FPO++ paper (Yi 2026) scales FPO to legged locomotion and humanoid motion tracking with sim-to-real on real Go2/Spot/H1/G1 hardware, adding numerical-stability tweaks (EMA of policy weights, beta-distribution τ sampling, multiple trust-region modes, kNN entropy bonus, adaptive KL-LR schedule).

Our goal is to bring FPO into this repo as a **first-class on-policy algorithm** that drops in alongside `train_ppo.py` and reuses our env presets, eval pipeline, and recording tools, so we can A/B it against Gaussian PPO on the tasks we actually care about (Playground locomotion + Go2 sim-to-real eventually).

## Goal

Port the **vanilla FPO algorithm** (akanazawa baseline) into our existing JAX/Flax repo, written in our repo's idioms (not vendored as a parallel package). Validate it against Gaussian PPO on a multimodal toy task and one Playground locomotion task before considering FPO++ extensions.

**Success criteria:**

1. `jax_rl/algos/fpo.py` exists, structurally parallel to `ppo.py`: same `TrainingState`/`init`/`update`/`select_action`/`select_action_eval` interface, same asymmetric actor-critic option, same `lax.scan` update.
2. `scripts/train_fpo.py` mirrors `scripts/train_ppo.py` CLI shape — same env-preset and seed flags, plus FPO-specific knobs (`--flow-steps`, `--n-samples-per-action`).
3. Unit-level tests pass for: CFM loss math, time embedding, Euler ODE sampler convergence, and one-update-step loss reduction on synthetic data.
4. **Validation gate A:** GridWorld multimodal task — FPO ≥ Gaussian PPO end-of-training return (reproduces akanazawa Fig. 4 directionally).
5. **Validation gate B:** One Playground locomotion task FPO trains to within 90% of Gaussian PPO's final return on equivalent compute budget. Wall-clock penalty must be measured and reported (expected: 2–4× slower per env-step due to ODE rollout cost).
6. No regressions in `train_ppo.py` — existing PPO path untouched. `RolloutBatch` extension uses optional fields with `None` default.
7. Doc sweep: `.context/AGENT_HANDOFF.md` Quick Reference updated, CLI ref regenerated (`docs/scripts/gen_cli_reference.py`), journal entry, lesson if novel.

## Non-goals

- **Not implementing FPO++ in this plan.** The numerical-stability tricks (EMA, beta τ, kNN entropy, adaptive KL, multi-trust-region) are deferred to a follow-up plan that depends on this MVP working. Same author group, same conceptual algorithm — separate engineering effort.
- **Not implementing DPPO / denoising-MDP mode.** akanazawa includes `loss_mode = "denoising_mdp"` for DPPO-style ablations; we're shipping `loss_mode = "fpo"` only. We can add it later if we want a head-to-head.
- **Not BC pretraining.** Manipulation experiments in the FPO++ paper depend on `pretrain_flow_bc.py` → RL fine-tune. Locomotion (our use case) trains from scratch — we mirror that.
- **Not deploying to Go2 hardware.** ONNX export of a flow policy with baked-in ODE integrator is a real engineering task (parallels our existing obs-norm-baked ONNX pattern but adds the Euler unroll). Out of scope for this plan; flagged for a follow-up.
- **Not refactoring `ppo.py`.** Any temptation to factor a shared base class between `ppo.py` and `fpo.py` is rejected (matches repo philosophy: "No Trainer base class, no BaseAlgorithm ABC"). They share their `Actor` builder pattern and rollout buffer; that's enough.
- **Not vendoring akanazawa/playground as a sibling package.** We discussed Option B (drop their `playground/` subdir in standalone for fast validation) and rejected it: two PPO codebases competing for mental space, can't reuse our env presets / record_video / future deploy. We're taking the cost of a clean port.
- **Not changing `RolloutBuffer` storage format on disk.** New optional fields default to `None`; PPO consumers ignore them. FPO consumers populate them.

### Algorithm core (vanilla FPO, akanazawa flavor)

**Flow vector field net.** MLP `v_θ(x_τ, τ_embed, h_obs) → action_dim`, where `x_τ = (1-τ)·a + τ·ε`. `τ` is sinusoidal-embedded with frequencies `2^i` (akanazawa default `timestep_embed_dim = 8`). Inputs concatenated. Output scaled by `policy_mlp_output_scale` (default `0.25`) — small init to keep early actions near zero. Width 32 × depth 4 in akanazawa playground; we'll use a config-driven hidden_dim that defaults to match repo's PPO actor width.

**Output mode.** akanazawa supports two:
- `"u"` — predict velocity, supervise `(v_pred − (ε − a))²`.
- `"u_but_supervise_as_eps"` (default) — predict velocity, reconstruct `x1_pred = x_τ + (1-τ)·v_pred`, supervise `(ε − x1_pred)²`. More stable in practice.

We implement both; default to `"u_but_supervise_as_eps"` to match akanazawa's measured-better default.

**Sampling.** Euler integrator, `flow_steps = 10` discrete steps (akanazawa default), τ schedule `linspace(1.0, 0.0, flow_steps + 1)`. Sampler runs **detached** during rollout (`jax.lax.stop_gradient` boundary at the rollout/update interface). Optional `feather_std` Gaussian perturbation on the final action for extra exploration (default 0).

**Training-time CFM loss.** Per stored action, sample `n_samples_per_action` (default 8) `(τ, ε)` pairs at rollout time. Cache them in `RolloutBatch`. During the update:

```
L_CFM(θ; o, a, τ, ε) = mean over action dims of (target − pred)²
```

with `target` and `pred` per the chosen output mode. This `(τ, ε)` cache is the FPO equivalent of PPO's stored `log_prob_old` — same role, different bytes.

**Ratio.**
```
ρ = exp( mean(L_CFM_old) − mean(L_CFM_new) )       # average_losses_before_exp = True (default)
```
or
```
ρ = exp( clip(L_CFM_old − L_CFM_new, -3, +3) )     # average_losses_before_exp = False
```
The clipped form reduces ratio variance. Both are in akanazawa; we expose via config and default to averaged-before-exp.

**PPO surrogate.** Standard clip:
```
loss_policy = -mean( min(ρ·A, clip(ρ, 1±ε_clip)·A) )
loss_value  = ½·mean( (V_θ − V_target)² )  · v_coef
loss_total  = loss_policy + loss_value
```

No entropy bonus (no closed form for a flow policy). `ε_clip` defaults to akanazawa's `0.05` (tighter than Brax PPO's `0.2`, which makes sense given the biased ratio).

**Update.** Single `optax.adam` (akanazawa) — different from our PPO's split actor/critic optimizers. We mirror akanazawa here: one optimizer, one combined loss. Keep value-loss-coef configurable so users can re-derive split-optimizer behavior if they want.

**`τ` schedule for training.** akanazawa default `discretize_t_for_training = True`: τ samples drawn from the same discrete schedule used for sampling. Alternative: continuous Uniform[0, 1]. We expose both.

### Buffer extension

`RolloutBatch` is a NamedTuple with already-optional fields (`advantages`, `returns`, `contraction_c`, etc.). Add three more, all defaulting to `None`:

```python
flow_eps: jax.Array | None = None        # (T, E, n_samples, action_dim)
flow_tau: jax.Array | None = None        # (T, E, n_samples, 1)
flow_init_cfm_loss: jax.Array | None = None  # (T, E, n_samples)
```

`RolloutBuffer.__init__` and `.add()` accept these as optional kwargs; PPO callers pass nothing, FPO callers pass the cached `(ε, τ, L_CFM_at_old_θ)`. Memory overhead: `8 × action_dim` floats per stored timestep. For 12-d Go2 actions, 8 samples, 1024 envs × 32 unroll: ~12 MB. Negligible.

### Asymmetric actor-critic

Existing PPO supports policy-obs vs critic-obs decoupling. Flow head conditions on **policy obs only** (the actor's view). Critic is unchanged. We pass through whatever `critic_obs_dim` arrangement the existing code does.

### `select_action` interface

PPO's `_select_stochastic` returns `(action, log_prob, value)`. FPO returns `(action, action_info, value)` where `action_info` is a small NamedTuple `FlowActionInfo(eps, tau, init_cfm_loss)` of cached MC samples. `train_fpo.py` unpacks accordingly. `select_action_eval` for record_video / deploy returns just the action (deterministic mode = zero feather noise, fixed seed for `(τ, ε)` traversal).

### Config

`FPOConfig` mirrors `PPOConfig` field-for-field where possible (encoder, num_envs, num_steps, num_epochs, minibatch_size, gamma, gae_lambda, clip_eps, value_loss_coef, learning_rate, normalize_advantage), then adds:

```python
flow_steps: int = 10
output_mode: Literal["u", "u_but_supervise_as_eps"] = "u_but_supervise_as_eps"
timestep_embed_dim: int = 8
n_samples_per_action: int = 8
average_losses_before_exp: bool = True
discretize_t_for_training: bool = True
feather_std: float = 0.0
policy_mlp_output_scale: float = 0.25
loss_diff_clip: float = 3.0  # Used only when average_losses_before_exp = False
flow_hidden_dim: int = 32     # akanazawa default
flow_n_layers: int = 4
```

### Validation strategy

We validate FPO incrementally — narrow tests before full training:

1. **Unit tests (Phase 1–4).** CFM loss correctness (analytical case), time embedding shape/values, Euler sampler converges to delta when ground-truth velocity field is constant, one-update-step loss reduction on synthetic flow data.
2. **Integration smoke (Phase 5).** Train 1k env-steps on smallest Playground task. Assert loss is finite, ratio statistics in plausible range, no JAX shape errors.
3. **Validation gate A — GridWorld.** Reproduce akanazawa's multimodal toy result. They show FPO captures both action modes; Gaussian PPO collapses to one. We won't replicate the env exactly — just demonstrate FPO ≥ PPO on a 2D multimodal action task we mock up.
4. **Validation gate B — Playground locomotion.** A task we already PPO-benchmark (e.g., `BarkourJoystick` if present, or another locomotion task). FPO trains to within 90% of PPO's final return on the same env-step budget. Report wall-clock delta.
5. **Wall-clock measurement.** Time `train_fpo.py` vs `train_ppo_fast.py` on 5M env-steps, same hardware. Document in journal.

### Risks & mitigations

| Risk | Mitigation |
|------|-----------|
| ODE rollout cost makes training too slow | Measure early (Task 16), parameterize `flow_steps` low (4–10), document delta |
| CFM ratio variance with N_mc=1 destabilizes training | Default `n_samples_per_action = 8` (akanazawa), expose as flag; use `average_losses_before_exp = True` |
| Single optimizer breaks asymmetric A/C balance | Keep `value_loss_coef` configurable; if needed, gate behind `--split-optimizer` flag (deferred) |
| Tanh squash interaction unclear | akanazawa does NOT squash. We follow that — outputs are unbounded by default. Action clipping happens at env boundary as today |
| `RolloutBatch` extension breaks PPO | All new fields are `Optional[Array] = None`; PPO never touches them. Run existing PPO smoke test as part of validation |
| Bias of CFM ratio (Jensen) under negative advantages | akanazawa does not specially handle. FPO++ does (asymmetric clamp). Defer; rely on tighter `ε_clip = 0.05` to bound damage |

## Out of scope (explicit follow-ups)

- **FPO++ extensions.** EMA, beta τ, kNN entropy, adaptive KL, multi-trust-region — separate plan, depends on this one passing validation gate B.
- **DPPO / denoising-MDP loss mode.** akanazawa's second `loss_mode`. Deferred. Useful for head-to-head ablation only.
- **ONNX export with baked Euler integrator.** Required for Go2 deploy. Parallels existing obs-norm bake-in pattern but with a `lax.scan` over flow steps that has to round-trip through ONNX. Separate plan.
- **BC pretrain → RL fine-tune.** For manipulation tasks. Different paradigm; not what we use FPO for first.
